# Життєвий Цикл Ордера та Потік Виконання в Системі Aurora

**Версія:** 1.0
**Дата:** 2025-10-26

## 1. Мета документа

Цей документ детально описує процес прийняття торгових рішень та виконання ордерів у системі. Мета — надати повне розуміння того, **які сигнали** використовуються, **як на їх основі формується торговий намір**, **які типи ордерів** створюються, та **в якому форматі** вони відправляються на біржу.

## 2. Фаза 1: Генерація Сигналу (Signal Generation)

Все починається з сирих ринкових даних, які перетворюються на стандартизовані аналітичні сигнали.

**Вхідні дані:**
-   Потоки ринкових даних з біржі (через `MarketDataConnector`):
    -   `bookTicker`: Дані про найкращі ціни купівлі (bid) та продажу (ask) та їх обсяги.
    -   `trade`: Дані про кожну окрему угоду, що відбулася на ринку.

**Процес (в домені `FeatureEngineering`):**
1.  **Розрахунок OBI (Order Book Imbalance):**
    -   **Формула:** `(bid_volume - ask_volume) / (bid_volume + ask_volume)`
    -   **Інтерпретація:** Показник дисбалансу в книзі ордерів. Позитивне значення вказує на тиск покупців, негативне — на тиск продавців.
2.  **Розрахунок TFI (Trade Flow Imbalance):**
    -   **Логіка:** Аналізує потік угод, підсумовуючи обсяги угод, що відбулися за ціною покупця (агресивні продажі) та ціною продавця (агресивні покупки).
    -   **Інтерпретація:** Показник агресії на ринку. Позитивне значення — домінують агресивні покупки, негативне — агресивні продажі.
3.  **Розрахунок `delta_price`:**
    -   **Логіка:** Зміна ціни за короткий проміжок часу.
    -   **Інтерпретація:** Показник локальної волатильності та імпульсу.
4.  **Розрахунок `absorption`:**
    -   **Логіка:** Оцінює, наскільки ринок "поглинає" великі ринкові ордери без значної зміни ціни.
    -   **Інтерпретація:** Висока абсорбція може вказувати на наявність великих лімітних ордерів, що стримують ціну.

**Вихід:**
-   Подія `EVT:FEATURES_CALCULATED` з набором числових значень (features) для конкретного інструменту (напр., ETHUSDT).

## 3. Фаза 2: Прийняття Рішення (Decision Making)

На цьому етапі система агрегує всі доступні дані для прийняття зваженого рішення.

**Вхідні дані (в домені `DecisionMaking`):**
1.  `EVT:FEATURES_CALCULATED` (з `FeatureEngineering`)
2.  `EVT:RISK_ASSESSMENT_COMPLETED` (з `RiskManagement`)
3.  `EVT:PORTFOLIO_STATE_UPDATED` (з `PositionTracking`)
4.  `EVT:REGIME_DETECTED` (з `RegimeDetector`)

**Процес:**
1.  **Розрахунок `signal_score`:**
    -   **Логіка:** Зважена сума основних фіч (OBI, TFI, absorption). Ваги (`signal_weights`) беруться з конфігурації (`trading.yaml`).
    -   **Приклад:** `signal_score = (obi * 0.4) + (tfi * 0.4) + (absorption * 0.2)`
2.  **Визначення Напрямку (`side`):**
    -   Якщо `signal_score > signal_threshold` (напр., 0.2) → `side = "buy"` (LONG).
    -   Якщо `signal_score < -signal_threshold` → `side = "sell"` (SHORT).
    -   Інакше → **Рішення не приймається (нейтральний сигнал).**
3.  **Перевірка Ринкового Режиму (Regime Filter):**
    -   Система перевіряє поточний ринковий режим (напр., `TREND_UP`, `TREND_DOWN`).
    -   **Логіка:** Блокуються контртрендові сигнали. Наприклад, у режимі `TREND_UP` сигнал `side = "sell"` буде заблокований.
4.  **Розрахунок Розміру Позиції (Position Sizing):**
    -   **Базовий розмір:** Розраховується на основі **дробу Келлі**, скоригованого на консервативні фактори (`kelly_alpha`, `kelly_conservative_factor`).
    -   **Обмеження (Caps):** Фінальний розмір позиції в USD є **мінімальним** з наступних значень:
        1.  Розмір, розрахований по Келлі.
        2.  Ліміт на основі ризику (`trade_cvar95_max_bps` від загального капіталу).
        3.  Ліміт ліквідності (`liquidity_based_cap_usd`).
    -   **Перевірка мінімального розміру:** Якщо фінальний розмір в USD менший за `min_position_size_usd`, угода відхиляється.
5.  **Конвертація в Кількість Активу (`qty`):**
    -   **Формула:** `qty_raw = final_pos_size_usd / current_price`
    -   **Округлення:** `qty` округлюється **вниз** до найближчого значення, кратного `step_size` інструмента (напр., 0.001 для BTC). Це робиться за допомогою `Decimal.quantize`, щоб уникнути помилок точності.
    -   **Перевірка:** Якщо після округлення `qty` дорівнює нулю, угода відхиляється.
6.  **Формування Торгового Наміру (`Trade Intent`):**
    -   Якщо всі перевірки пройдені, система генерує об'єкт `TradeIntent`.

**Вихід:**
-   Подія `EVT:TRADE_INTENT_PROPOSED` зі структурою, що відповідає схемі `trade_intent.schema.json`.

## 4. Фаза 3: Виконання Ордера (Order Execution)

На цьому етапі торговий намір перетворюється на конкретну команду для біржі.

**Вхідні дані:**
-   Подія `EVT:TRADE_INTENT_PROPOSED`.

**Процес:**
1.  **Трансформація (Bridge):**
    -   Обробник `on_trade_intent_proposed` у `main.py` перетворює аналітичний `EVT:TRADE_INTENT_PROPOSED` на виконавчу команду `CMD:OPEN`.
    -   Ключові поля (символ, сторона, кількість, ціна) копіюються.
2.  **Обробка в `ExecPosFSM`:**
    -   Команда `CMD:OPEN` надходить до `OpenFlowFSM` для відповідного символу.
    -   **Ідемпотентність:** Перевіряється `idempotent_key`. Якщо команда з таким ключем вже оброблялася нещодавно, вона відхиляється.
    -   **Гарди (Guards):** Проводяться фінальні перевірки:
        -   **Cooldown:** Чи не надто часто надсилаються ордери?
        -   **Min Notional:** Чи відповідає вартість ордера (`qty * price`) мінімальному ліміту біржі?
3.  **Формування Ордера для Біржі:**
    -   Якщо всі гарди пройдені, `OpenFlowFSM` генерує `DEC:OPEN`.
    -   Це повідомлення передається до **Адаптера** (`BinanceExecutionAdapter`).
    -   Адаптер форматує дані у специфічний для Binance API запит.

**Вихід (Типи та Формати Ордерів):**

На даний момент система генерує **один основний тип ордера** для входу в позицію:

-   **Тип Ордера:** `LIMIT` (Лімітний ордер)
    -   **Чому `LIMIT`?** Це дозволяє контролювати ціну входу і потенційно отримувати комісію "мейкера" (maker fee).
    -   **Ціна (`price`):** Встановлюється на основі `price_ref` з `TradeIntent`, яка, в свою чергу, береться з поля `price` у `features`. Це, по суті, остання відома ринкова ціна.
    -   **Час в силі (`timeInForce`):** `GTC` (Good-Till-Cancel) - ордер буде активним, доки не буде виконаний або скасований.

**Формат відправки на біржу (приклад для `DEC:OPEN`):**
-   **Повідомлення в системі:**
    ```json
    {
      "op": "DEC",
      "verb": "OPEN",
      "pld": {
        "symbol": "ETHUSDT",
        "side": "BUY",
        "qty": "0.123",
        "price": "4000.98",
        "order_type": "LIMIT",
        "tif": "GTC",
        "idempotent_key": "..."
      }
    }
    ```
-   **Запит до Binance API (спрощено):**
    ```
    POST /fapi/v1/order
    {
      "symbol": "ETHUSDT",
      "side": "BUY",
      "type": "LIMIT",
      "quantity": "0.123",
      "price": "4000.98",
      "timeInForce": "GTC",
      "newClientOrderId": "..."
    }
    ```

**Важливо:** Ордери для закриття позиції (Stop Loss, Take Profit), які генеруються в `ManageFlowFSM`, також використовують `LIMIT` (для Take Profit) та `STOP_MARKET` (для Stop Loss) з прапором `reduceOnly=true`, щоб гарантувати, що ці ордери можуть лише закрити існуючу позицію, а не відкрити нову.

## 5. Висновок

Система використовує багаторівневий підхід до прийняття рішень, де сирі дані послідовно збагачуються, фільтруються через ризик-менеджмент та ринкові режими, і лише потім перетворюються на конкретний, валідований **лімітний ордер**, який відправляється на біржу. Кожен крок цього процесу логується і має чіткий "причинний слід" для подальшого аналізу.
