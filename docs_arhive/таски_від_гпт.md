# Задание для Copilot (RU) — 1/2

**TASK_ID:** `FSMP-P0-T03`
**Title:** Конкурентобезопасный WAL и атомарная идемпотентность (locks + CAS)
**Branch:** `fix/p0-wal-and-idem-locks`

## Цели (DoD/Gates)

1. **WAL:** устранить race при append: единственная корректная цепочка `prev_hash→hash` даже при N конкурентных записей (мультипоточно/мультипроцессно).
2. **Idempotency:** «single-flight» на `idempotent_key`: для конкурентных запросов с одним ключом выполняется ровно один handler, прочие получают `dedup:true`/`inflight:true` без побочного эффекта.
3. **Fail-closed:** при невозможности захватить необходимые замки ≤ `lock_timeout_ms` → возврат 503/429, **без записи** в WAL.
4. **Тесты:** воспроизвести гонки и подтвердить отсутствие нарушений цепочки и дублей; покрытие ≥ 90%.

## Ограничения

* Contract-first: интерфейсы публичных эндпоинтов не ломаем; добавления — назад совместимы.
* Additive-only: новый слой синхронизации/замков и CAS-проверок; существующую бизнес-логику не изменять.
* Лёгкий XAI: фиксируем короткие `why` для путей «LOCK_ACQUIRED / LOCK_TIMEOUT / IDEM_DEDUP / IDEM_INFLIGHT».

## Изменения по файлам (точечно)

```
vfoundation/dr/wal.py
  + WALFileLock: кросс-платформенная эксклюзивная блокировка файла (fcntl|msvcrt; абстракция внутри).
  ~ append(...):
      - Захватить file lock (LOCK_EX).
      - Прочитать хвост → вычислить prev_hash.
      - Сформировать запись, посчитать hash.
      - Атомарная запись (файл открыт с O_APPEND; после записи при необходимости fsync).
      - Освободить lock.
  + append_cas(expected_prev_hash?): если задан и не совпал с фактическим хвостом → вернуть CONFLICT (409) без записи.
  + verify_chain(records)->bool: использовать при /debug и /replay.
  + метрики: счетчик lock_contention, lock_wait_ms (для /metrics).

vfoundation/core/idempotency.py
  + KeyedLocks: «single-flight» на ключ (внутрипроцессные локи по idempotent_key; с TTL-освобождением).
  + Inflight registry: состояния {pending, done(result)} c TTL.
  ~ API:
      - begin(key) -> {"acquired":true}|{"inflight":true}
      - complete(key, result)  # сохраняет результат для последующих "догоняющих" запросов в пределах TTL
      - get_if_done(key) -> Optional[result]
      - remember_dedup(key)  # старое поведение для уже завершенных

vfoundation/core/routing.py
  ~ Порядок:
      1) Проверить валидность контракта (why≤80, TTL ok) — иначе 400, без WAL.
      2) Идемпотентность:
         - если get_if_done(key) есть → вернуть cached result (dedup:true).
         - иначе begin(key): если inflight → вернуть 202/209 с {"inflight":true} (без WAL).
         - если acquired → переходим к обработке.
      3) При успешном handler: записать в WAL; complete(key, result); вернуть 200.
      4) При исключении: complete(key, error as ERR); возврат 500/4xx.
  + Логи/метрики: idem_acquired, idem_inflight, idem_dedup.

vfoundation/obs/debug_api.py
  ~ /debug/{rid}, /replay/{rid}: включить verify_chain() и поля integrity_ok (true/false).

docs/ADR-004-WAL-Concurrency.md  (новый)
  - Решение: file-lock + O_APPEND; опциональный CAS; причины отказа от «беззамковых» стратегий при мультипроцессе.
```

## Алгоритмические детали (без кода)

* **WAL file-lock:**

  * На время «прочитать хвост → записать новую запись» держать **эксклюзивный** замок файла.
  * На Unix — `fcntl.flock(LOCK_EX)`, на Windows — `msvcrt.locking()`. Обернуть в единый helper.
  * Открывать файл с `O_APPEND`; это гарантирует атомарность «смещения позиция→запись» для одного процесса; но чтение хвоста без lock недопустимо → поэтому lock обязателен.
  * По желанию: `append_cas(expected_prev_hash)` для оптимистической схемы (в будущем).

* **Idempotency single-flight:**

  * Первому конкурентному запросу по ключу — `acquired:true` (он выполняет handler).
  * Остальные получают `inflight:true` (можно 202, но в нашем P0 достаточно `200{"inflight":true}` либо `209` если принято).
  * По завершении первый кладёт результат в кэш (TTL) — догоняющие читают готовый результат как `dedup:true`.
  * Межпроцессная идемпотентность в P0 не вводится (наш Router — single worker по умолчанию). Для multi-worker добавим Redis-lock в P1/P2.

## Тест-план (часть 1, в этом PR)

* **WAL race (threaded):** 100 конкурентных append → `verify_chain=True`, длина N, ни одного «выпавшего» звена.
* **WAL race (multiprocess, optional):** 8 процессов × 100 append → цепь валидна (Linux CI — обязательный; Windows — best-effort).
* **Idem single-flight:** 50 потоков с одинаковым `idempotent_key` → 1 вызов handler; остальные `inflight:true` или получают тот же cached result; в WAL — ровно 1 запись на ключ.
* **Fail-closed:** искусственно замедлить удержание lock → часть вызовов получает 503 (lock timeout), и в WAL нет лишних записей.
* **Метрики:** lock_contention > 0 под стрессом; timeout_rate ≤ 1% в smoke.

## Метрики/перф

* Цель: удержание file-lock ≤ 2–5 мс на обычных записях.
* p95(router) не ухудшить > +2 мс относительно дофиксов (см. /metrics).

* ADR-004, список изменений, логи стресс-тестов, coverage ≥90%, обновлённые чек-боксы P0, запись в JOURNAL (`FSMP-P0-T03`).

**Коммит:** `fix(p0): WAL file-lock + single-flight idempotency; integrity checks [FSMP-P0-T03]`

**Scope (строго минимум):**

1. **Папки/файлы (создай при отсутствии, не трогай остальное):**

* `core/adapters/execution_exceptions.py` — нормализованные ошибки SDK→ERR.
* `core/adapters/idempotency_ledger.py` — легкий локальный ledger (in-proc) для submit/cancel (exactly-once по ключу).
* `configs/adapter.yaml` — параметры retry/CB/timeouts/limits.
* `tests/adapters/test_execution_adapter_*.py` — тесты из раздела “Тесты”.

2. **API адаптера (тонкий слой над ACL):**

* `submit(order_dto) -> EVT:ORDER_PLACED | EVT:REJECTED`
* `cancel(order_id|client_order_id) -> EVT:CANCELLED | EVT:REJECTED`
* `stream()` (генератор/асинх. итератор) SDK-событий → маппинг в `EVT:PARTIAL_FILL|FILL|EXPIRED|REJECTED`.

3. **Идемпотентность (граница адаптера):**

* `client_order_id = hash64(symbol, side, qty, price_mode, reduce_only?, ts_bucket_1s, idempotent_key)`; тот же вход → тот же id.
* Повторные `submit`/`cancel` с тем же ключом — **no-op** (верни last-known EVT).
* Ledger хранит минимум: `{key, first_seen_ts, last_status, last_payload_digest}`.

4. **Надёжность:**

* **Retry**: экспоненциальный backoff с джиттером; лимиты из `configs/adapter.yaml`.
* **Circuit Breaker**: `open_threshold_error_rate`, `cooldown`, `half_open_probes`. В `OPEN` — `ERR.adapter.cb_open` (WHY≤80).
* **Timeouts**: на все I/O вызовы; по таймауту — чёткое ERR-сообщение с нормализованным кодом.
* **Rate-limits**: уважай бюджет запросов; при исчерпании — короткая спячка + счётчик `sdk_retries_total`.

5. **Конфиг/секреты (только ENV, чтение уже через `config.py`):**

* `EXECUTION_MODE ∈ {dry_run, paper, live}`; **default= dry_run**.
* `EXCHANGE_API_KEY`, `EXCHANGE_API_SECRET`, `EXCHANGE_BASE_URL`, `EXCHANGE_WS_URL`.
* `ADAPTER_SUBMIT_TIMEOUT_MS`, `ADAPTER_CANCEL_TIMEOUT_MS`, `ADAPTER_STREAM_TIMEOUT_MS`.
* `ADAPTER_RETRY_MAX_ATTEMPTS`, `ADAPTER_RETRY_BASE_MS`, `ADAPTER_RETRY_MAX_MS`.
* `ADAPTER_CB_OPEN_THRESHOLD`, `ADAPTER_CB_COOLDOWN_MS`, `ADAPTER_CB_HALF_OPEN_PROBES`.
