# ДОКУМЕНТАЦІЯ ДОМЕНУ — decision_making

## 1) Огляд Домену

**Роль:**
Домен `decision_making` (прийняття рішень) є **центральною нервовою системою** конвеєра виконання торгів. Його основна відповідальність — приймати аналітичні дані (фічі, режими), стан ринку (ціни, стакан ордерів/order book) та обмеження ризиків для створення авторитарних **Торгових Намірів** (`EVT:TRADE_INTENT_PROPOSED`).

**Він НЕ відповідає за:**
- Розрахунок сирих фіч (це відповідальність `feature_engineering`).
- Виконання ордерів на біржі (це відповідальність `execution_position`).
- Управління довгостроковим станом портфеля (це відповідальність `position_tracking`).
- Сповіщення або маршрутизацію повідомлень (це відповідальність `telemetry`).

**Ключові випадки використання (Key Use-Cases):**
1.  **Генерація Сигналів:** Оцінює вхідні набори фіч відповідно до логіки стратегії (Aurora, Mean Reversion) для генерації сигналів на купівлю/продаж.
2.  **Гейтинг Ризиків (Risk Gating):** Застосовує суворі передторгівельні перевірки ризиків (оцінка ризику/risk score, просадка, кулдауни) до формування будь-якого наміру.
3.  **Сайзинг Позиції (Position Sizing):** Розраховує точну кількість для входу та цільовий номінал на основі поточного капіталу, конфігурації ризику та ліквідності ринку (`sizing_margin_first.py`).
4.  **Планування Життєвого Циклу Ордера:** Обчислює ціни Входу (Entry), Стоп-Лоссу (Stop Loss) та Тейк-Профіту (Take Profit) на основі волатильності (ATR) та дисбалансу стакану (OBI) (`entry_plan.py`).
5.  **Арбітраж:** Управляє конфліктами між кількома стратегіями (наприклад, гарантує, що `Aurora` та `MeanReversion` не конкурують за один символ одночасно).
6.  **Оркестрація Переворотів (Flip Orchestration):** безпечно керує переходом з Long -> Short (або навпаки), суворо дотримуючись життєвого циклу "Закрити -> Флет -> Відкрити" через Гістерезис.

**Інваріанти та Гарантії:**
-   **Fail-Closed (Відмова-Закриття):** Якщо будь-які критичні вхідні дані (Ціна, Оцінка Ризику, Готовність Фіч, Контекст Таймфрейму) відсутні або застарілі, домен **БЛОКУЄ** торгівлю. Він ніколи не перемикається в режим "Відкрито" за замовчуванням.
-   **Ідемпотентність:** Логіка стратегії приймає `rid` (ID запиту) або детерміновані мітки часу, щоб запобігти дублюванню обробки сигналів.
-   **Узгодженість Стану:** Використовує абстракцію `Clock` для всієї логіки, що залежить від часу (кулдауни, таймаути), щоб забезпечити детерміновану поведінку в бектестах.
-   **Суворий Контракт Конфігурації:** Відхиляє загальні конфігурації типу `dict`; вимагає типізованих Pydantic моделей (наприклад, `AuroraConfig`) для запобігання "тихим дефолтам".

## 2) Публічні Інтерфейси / Контракти

**Основні Точки Входу:**

1.  **`CMD:PROCESS_STRATEGY` (Команда)**
    *   **Обробник:** `AuroraHandler.on_process_strategy` / `MeanReversionHandler._on_process_strategy`
    *   **Вхід:** Дані бару, Фічі (Features), Стан прогріву/готовності (Warmup/Readiness), Контекст таймфрейму (`tf_sec`), `bar_close_ts`.
    *   **Вихід:** Потенційно випускає `EVT:STRATEGY_SIGNAL_PRODUCED`.
    *   **Побічні ефекти:** Оновлює внутрішній стан (прогрів, кеш режиму), логує метрики прийняття рішень.
    *   **Режими помилок:** Записує `trade_intent_rejected` в WAL, якщо вхідні дані недійсні/відсутні (наприклад, `NRR-MISSING-TF-SEC`).

2.  **`EVT:STRATEGY_SIGNAL_PRODUCED` (Подія)**
    *   **Обробник:** `DecisionMaking._on_strategy_signal_gateway`
    *   **Вхід:** Пейлоад сигналу (оцінка, сторона, причина `why`, готовність `readiness`).
    *   **Вихід:** Випускає `EVT:TRADE_INTENT_PROPOSED`, якщо всі гейти пройдені, або `EVT:STRATEGY_DECISION_BLOCKED` / `deferred` сигнал, якщо заблоковано.
    *   **Побічні ефекти:** Оновлює атомарні лічильники ризику (`intents_seen_total`), перевіряє глобальні гейти ризику/QoS.
    *   **Режими помилок:** Тихе відкидання, якщо сигнал недійсний; Планування повтору, якщо заблоковано через тимчасовий QoS (наприклад, `NRR-RISK-STALE`).

3.  **`EVT:REGIME_DETECTED` (Подія)**
    *   **Обробник:** `DecisionMaking.on_regime` (через обробники)
    *   **Вхід:** Мітка режиму (наприклад, `TREND_UP`, `HIGH_VOLATILITY`), впевненість, мітка часу.
    *   **Вихід:** Оновлює кешований стан режиму.
    *   **Побічні ефекти:** Оновлює "серцебиття" (liveness heartbeat) для захисного механізму детектора режимів.

**Явні Контракти:**
*   **`DecisionContext`**: Обгортає словники сирих фіч у типізований, безпечний об'єкт доступу (`TrendView`, `FlowView` тощо), який відстежує відсутні поля замість того, щоб спричиняти збої (crashing).
*   **`EntryPlan`**: Чисто функціональний клас, який гарантує дійсні ціни Entry/SL/TP (або викликає `ValueError`, якщо вхідні дані небезпечні для торгівлі).

## 4) Пофайлова Документація

### `decision_making.py`
-   **Призначення:** Основний контролер домену. Агрегує вхідні дані, управляє глобальним `DecisionContext` та забезпечує універсальні гейти (Ризик, QoS, Оркестрація Переворотів) перед випуском фінальних намірів.
-   **Ключові Символи:** `DecisionMaking` (клас), `_on_strategy_signal_gateway` (воротар/gatekeeper), `_check_strategy_arbitration`.
-   **Резюме Логіки:** Слухає сигнали -> Перевіряє Оцінку Ризику -> Перевіряє QoS/Кулдаун -> Перевіряє Експозицію -> Перевіряє Стан Перевороту -> Випускає запропонований намір.
-   **Ризики:**
    -   [КРИТИЧНИЙ] Десинхронізація стану `_pending_flips` може залишити позицію застряглою в стані "очікування закриття" без відкриття нової ноги.
    -   [ВИСОКИЙ] Спільний стан `_qos_state` між стратегіями може призвести до того, що одна "шумна" стратегія витіснить іншу.
-   **Примітки:** Нещодавно відрефакторено для використання `DecisionContext` та `AuroraConfig`.

### `aurora_handler.py`
-   **Призначення:** Реалізує логіку стратегії Aurora. Управляє станом, специфічним для Aurora (прогрів, зсув сторін/side bias, актуальність режиму).
-   **Ключові Символи:** `AuroraHandler`, `SymbolState`, `_process_decision`, `_emit_signal`.
-   **Резюме Логіки:** `on_process_strategy` -> валідує вхідні дані -> оновлює прогрів -> `AuroraScoringKernel.compute()` -> `_emit_signal`.
-   **Ризики:**
    -   [СЕРЕДНІЙ] Перевірка `warmup_full_ready` може бути занадто агресивною (Fail-Fast), що спричинить нуль угод під час тривалих прогрівів у бектестах.
    -   [НИЗЬКИЙ] Витік пам'яті в `_symbol_states` при торгівлі тисячами символів (малоймовірно в поточному обсязі).

### `mean_reversion_handler.py`
-   **Призначення:** Обробник для стратегії Mean Reversion (Смуги Боллінджера + RSI).
-   **Ключові Символи:** `MeanReversionHandler`.
-   **Резюме Логіки:** Приймає `CMD:PROCESS_STRATEGY`, парсить OHLCV бар, делегує `MeanReversion1mStrategy` (в домені FE), логує детальні дані бару.
-   **Ризики:**
    -   [СЕРЕДНІЙ] Покладається на перетин `_enabled_symbols` з `strategies_registry`. Якщо реєстр налаштовано неправильно, MR мовчить.

### `decision_context.py`
-   **Призначення:** Забезпечує безпечний з точки зору типів, семантичний вигляд словника сирих фіч. (Trend, Flow, Volatility Views).
-   **Ключові Символи:** `DecisionContext`, `TrendView`, `FlowView`, `create_decision_context`.
-   **Резюме Логіки:** Обгортки для ледачого парсингу навколо `features.get()`. Відстежує "відсутні" або "недійсні" поля для спостережуваності.
-   **Примітки:** Критично для запобігання падінням через помилки ключів або тихим дефолтам `0.0` у математичній логіці.

### `entry_plan.py`
-   **Призначення:** Обчислює ціни Entry, SL та TP. Сувора, чисто функціональна логіка.
-   **Ключові Символи:** `EntryPlan`, `EntryPlanParams`.
-   **Резюме Логіки:** `ref_price +/- (ATR * k)`. Модулює зміщення входу на основі OBI (Order Book Imbalance).
-   **Ризики:**
    -   [ВИСОКИЙ] Якщо `ATR` дорівнює 0 або None (і не вимагається), дистанція SL/TP стає `min_offset` (1bp). Використовуйте `require_atr=True` для безпеки.

### `aurora_scoring_kernel.py`
-   **Призначення:** Чисте математичне ядро для скорингу Aurora, щоб відокремити логіку від стану/IO.
-   **Ключові Символи:** `AuroraScoringKernel`, `ScoringResult`.
-   **Резюме Логіки:** Нормалізує вхідні дані -> Обчислює Direction Score -> Обчислює Strength Score -> Комбінує -> Застосовує множники Режиму/Зсуву (Bias).

### `sizing_margin_first.py`
-   **Призначення:** Ізольована логіка для розрахунку кількості (quantity) торгівлі на основі правил маржі.
-   **Ключові Символи:** `compute_notional_target`, `compute_qty`.
-   **Резюме Логіки:** `margin = equity * margin_pct`, `target = margin * leverage`. Округляє кількість вниз до розміру кроку (step size).

### `normalized_reject_reasons.py` & `why_codes.py`
-   **Призначення:** Константи та Enum-и для стандартизованого звітування про помилки (`NRR-xxx`, `WhyCode`).
-   **Ключові Символи:** `NormalizedRejectReasons` (клас), `WhyCode` (Enum).
-   **Резюме Логіки:** Мапить сирі рядки помилок/виключень у канонічні коди для аналітики.

### `trade_intent_reject_wal.py`
-   **Призначення:** Записує відхилені наміри у Write-Ahead Log (WAL) та консоль/телеметрію.
-   **Ключові Символи:** `write_trade_intent_rejected`.

### `schemas/trade_intent_v1.json`
-   **Призначення:** JSON Schema контракт для `EVT:TRADE_INTENT_PROPOSED`.
-   **Ключові Особливості:**
    -   Умовна валідація (Conditional Validation): `LIMIT` вимагає `tif` та `valid_for_ms`, `MARKET` забороняє `tif`.
    -   Regex Pattern Matching: Всі Decimal поля валідуються як рядки `^[0-9]+(\\.[0-9]+)?$`.

## 5) Об'єктивна Оцінка Якості

1.  **Коректність: 9/10**
    *   Логіка сильно і суворо типізована (Pydantic, `Decimal`). `DecisionContext` запобігає багам, пов'язаним з типами. Чисті функції (`EntryPlan`, Kernel) забезпечують тестованість.
    *   *Недолік:* Залежність від `CMD:PROCESS_STRATEGY` припускає, що upstream FE є ідеально надійним.

2.  **Безпека (Торговий Рівень): 9/10**
    *   **Fail-Closed** всюди. Гейтинг ризику є обов'язковим.
    *   **Анти-Пірамідинг** через Оркестрацію Переворотів.
    *   **Перевірки Санітарності (Sanity Checks):** `sizing_margin_first` запобігає негативним/нульовим кількостям. Логіка `normalization` обмежує (clamps) дикі значення фіч.

3.  **Підтримуваність: 8/10**
    *   Чіткий розділ відповідальності (Handler vs Kernel vs Domain).
    *   Константи централізовані в `why_codes.py`.
    *   *Недолік:* Клас `DecisionMaking` великий (~4000 рядків) і змішує оркестрацію з деякою застарілою логікою стану.

4.  **Тестованість: 10/10**
    *   Основна логіка (`EntryPlan`, `ScoringKernel`) не має побічних ефектів.
    *   Абстракція `Clock` дозволяє детерміноване тестування часу.
    *   Використовується Dependency Injection (передача `config`, `fsm`).

5.  **Спостережуваність: 9/10**
    *   Широке логування (`DM breadcrumbs`), стандартизовані `WhyCodes` та явні події `DecisionBlocked`.
    *   Вбудована підтримка форензики бектестів (`bar_logger`).

6.  **Ясність Контрактів: 8/10**
    *   Вхідні контракти (`CMD:PROCESS_STRATEGY`) добре визначені.
    *   Вихід (`EVT:TRADE_INTENT_PROPOSED`) стандартний.
    *   *Недолік:* Контракт словника "readiness" всередині `signals` фіч трохи неявний (покладається на збіг ключів).

## 6) Критичні Гіпотези

1.  **Блокування через Застарілі Дані Ризику (Циклічна Залежність):**
    *   **Гіпотеза:** `_on_strategy_signal_gateway` блокує, якщо `risk.ts` старіше за `features.ts`. Якщо Risk engine чекає на Decision engine, щоб прокинутися, система заходить у глухий кут (deadlocks).
    *   **Код:** `decision_making.py` -> `GATE 1.5: RISK SKEW GATE`.
    *   **Виправлення:** Забезпечити роботу Risk engine за незалежним таймером/тіком, а не "downstream" від подій Decision.

2.  **Гістерезис Перевороту - "Примарне" Закриття:**
    *   **Гіпотеза:** Переворот ініціює намір "Close", але виконання провалюється/відхиляється. Стан `_pending_flips` залишається в очікуванні заповнення "Close", яке ніколи не прийде. Нові сигнали блокуються назавжди.
    *   **Код:** Логіка `_handle_flip_orchestration` покладається на `EVT:ORDER_FILLED` або специфічний таймаут для очищення стану очікування.
    *   **Перевірка:** Перевірити наявність та роботу логіки `FlipTimeout`.

3.  **ATR Zero Fallback (Відкат до нульового ATR):**
    *   **Гіпотеза:** `EntryPlan` дозволяє `require_atr=False`. Якщо ATR відсутній, дефолтить до `0` -> `min_offset`. Це призводить до розміщення `STOP_LOSS` на відстані 1bp від входу, викликаючи негайний стоп-аут на шумі.
    *   **Код:** `entry_plan.py` рядок ~237 (`min_offset`).
    *   **Захист:** Забезпечити `require_atr=True` у продакшн конфігурації.

4.  **Блокування Прогріву "Fail-Fast" у Бектесті:**
    *   **Гіпотеза:** `AuroraHandler` перевіряє `warmup_full_ready`. У бектестах, якщо одна маловідома фіча ніколи не готова (наприклад, `funding_rate` на Spot), стратегія НІКОЛИ не торгує.
    *   **Код:** `aurora_handler.py` -> `_process_decision`.
    *   **Перевірка:** Перевірити доступність режиму `warn_only` для бектестів.

5.  **Тихий Гейт Ліквідності Kappa:**
    *   **Гіпотеза [ВИРІШЕНО]:** `MeanReversionHandler` перевіряє `_check_liquidity_gate`.
    *   **Статус:** **FIXED**. Тепер кидає явний `RuntimeError`, якщо `liquidity_kappa` відсутня. Fail-Fast реалізовано.
    *   **Код:** `mean_reversion_handler.py` -> `_check_liquidity_gate`.

## 7) Гіпотези Покращення

1.  **Єдиний Буфер Сигналів (Unified Signal Buffer):**
    *   **Ціль:** Централізувати арбітраж сигналів.
    *   **Причина:** Наразі `Aurora` та `MeanReversion` випускають сигнали незалежно. `DecisionMaking` арбітрує їх, але єдина черга пріоритетів була б чистішою для додавання 3+ стратегій.
    *   **План:** Створити компонент `SignalAggregator`, який діє як єдине джерело `EVT:STRATEGY_SIGNAL_PRODUCED`.

2.  **Відокремлення Логіки "Перевороту" (Flip) від DecisionMaking:**
    *   **Ціль:** Спростити `DecisionMaking`.
    *   **Причина:** "Переворот" (Закрити потім Відкрити) — це турбота *Виконання* або *Управління Позицією*. `DecisionMaking` ідеально має просто казати "Я хочу бути Long". Домен `Execution` має обробляти механіку "Закрити Short потім Відкрити Long".
    *   **План:** Перемістити `_handle_flip_orchestration` в `execution_position` або новий домен `OrderOrchestrator`.

3.  **Явний Стан "Система Не Готова":**
    *   **Ціль:** Зменшити шум у логах.
    *   **Причина:** Наразі випускає `NRR-DATA-NOT-READY` для кожного тіку під час прогріву.
    *   **План:** Реалізувати FSM рівня домену `SystemStatus` (Boot -> Warmup -> Active). Пригнічувати окремі попередження про торгівлю під час Warmup.

4.  **Типізовані Пейлоади Подій:**
    *   **Ціль:** Безпека контракту.
    *   **Причина:** Пейлоад `EVT:STRATEGY_SIGNAL_PRODUCED` створюється як сирий `dict`.
    *   **План:** Визначити Pydantic модель `StrategySignalPayload` у `schemas.py` та забезпечити її використання в обробниках.

5.  **Динамічні Ліміти QoS:**
    *   **Ціль:** Адаптація до волатильності ринку.
    *   **Причина:** Фіксований `qos_max_intents_per_minute` може бути занадто обмежувальним під час подій високої волатильності, коли потрібні швидкі коригування.
    *   **План:** Масштабувати ліміти QoS на основі `regime` (наприклад, 2x ліміти в `HIGH_VOLATILITY`).

## 8) План Тестування

**Сценарій 1: Базовий Вхід у Long**
*   **Умова:** Позиція Flat, `Analysis` каже BUY (Score > Threshold), Risk OK, Готівка є.
*   **Очікування:** Випускає `EVT:TRADE_INTENT_PROPOSED` зі стороною side=BUY, розумною кількістю (qty) та лімітною ціною.

**Сценарій 2: Блокування Ризиком**
*   **Умова:** `Analysis` каже BUY, але `RiskScore` = 1.0 (Макс 0.8).
*   **Очікування:** Випускає `EVT:STRATEGY_DECISION_BLOCKED` (Причина: `RISK_SCORE_HIGH`). Жодного наміру.

**Сценарій 3: Переворот (Long -> Short)**
*   **Умова:** Позиція Long. `Analysis` каже STRONG SELL.
*   **Очікування:**
    1.  Випускає `EVT:TRADE_INTENT_PROPOSED` (Дія: CLOSE, Сторона: SELL).
    2.  Чекає на заповнення (fill).
    3.  Випускає `EVT:TRADE_INTENT_PROPOSED` (Дія: OPEN, Сторона: SELL).

**Сценарій 4: Гейт Застарілих Даних**
*   **Умова:** Feature TS = T, Risk TS = T-60s (Поріг 30s).
*   **Очікування:** `EVT:STRATEGY_DECISION_BLOCKED` (Причина: `NRR-RISK-STALE`).

**Сценарій 5: Порушення Контракту Конфігурації**
*   **Умова:** Передати `dict` замість `AuroraConfig` у `DecisionMaking.__init__`.
*   **Очікування:** `TypeError` викликається негайно (Fail-Fast).

**Сценарій 6: Валідації EntryPlan**
*   **Умова:** ATR від'ємний або нуль (і вимагається).
*   **Очікування:** `EntryPlan.compute` викликає `ValueError`. Обробник ловить і логує помилку, сигналу немає.

**Сценарій 7: Недостатній Капітал**
*   **Умова:** `available_usdt` < `min_position_size`.
*   **Очікування:** `sizing_margin_first` повертає 0 qty. `DecisionMaking` блокує з `SIZING_FLOORED_BY_MIN_SIZE`.

**Сценарій 8: Обмеження Швидкості QoS (Rate Limit)**
*   **Умова:** Сигнал згенеровано через 100мс після попереднього сигналу для того ж символу (Ліміт: 1/сек).
*   **Очікування:** Сигнал відкинуто/відкладено. `EVT:STRATEGY_DECISION_BLOCKED` (Причина: `GUARD_RATE_LIMIT_EXCEEDED` або Cooldown).

**Сценарій 9: Фільтрація Режимів**
*   **Умова:** Стратегія `MeanReversion`, Режим = `TREND_UP`. Конфігурація: `allowed_regimes=['FLAT']`.
*   **Очікування:** Сигнал придушено всередині Обробника.

**Сценарій 10: Ідемпотентність**
*   **Умова:** Повторити точно таке ж повідомлення `CMD:PROCESS_STRATEGY` з тим самим `rid`.
*   **Очікування:** Домен, ймовірно, обробить його знову, *якщо* не активний специфічний кеш дедуплікації `rid` (Перевірте логіку перевірки `_last_successful_features_ts`).

## 9) Червоні Прапорці ("Аудит одного екрану")

1.  **Відсутній `tf_sec`**: Якщо в `CMD:PROCESS_STRATEGY` відсутній таймфрейм, Обробник тихо відкидає або відхиляє. Основна причина "тихої смерті".
2.  **Лаг `risk.ts`**: Якщо Risk Engine повільний (kafka lag), Decision Engine блокує ВСІ угоди (Fail-Closed).
3.  **`DecisionMaking.py` > 4000 LOC**: Висока складність, важко перевірити побічні ефекти за один прохід.
4.  **Неявний Доступ до Словника**: Деякі застарілі частини можуть все ще використовувати `pld.get("key")` без валідації схеми, ризикуючи поширенням `None`.
5.  **Залипання Стану Перевороту**: `_pending_flips` знаходиться в пам'яті. **Перезапуски стирають цей стан**, потенційно залишаючи "сироту" — закриту позицію, яка ніколи не відкриває ногу перевороту.
6.  **Математика з Плаваючою Комою**: Використовує `Decimal` переважно, але існують деякі конвертації `float` у помічниках скорингу. Слідкуйте за проблемами точності.
7.  **Магічні Числа**: `420` (Side Bias Window), `0.72` (Target Ratio) – визначені в дефолтах конфігурації, але критичні для поведінки.
8.  **Порожній `strategies_registry`**: Якщо реєстр порожній, `check_arbitration` може заблокувати все або дозволити все залежно від дефолтного фолбеку.
9.  **Синхронізація Часу**: Використовує абстракцію `Clock`, але якщо `wall_time_fn` і `monotonic_fn` розходяться (наприклад, перекіс системного годинника), логіка кулдаунів ламається.
10. **Нульова Кількість**: `sizing_margin_first` округляє вниз до 0 для малих акаунтів/високих цін. Користувач бачить "No Trade" без помилки, якщо рівень логування не DEBUG.
11. **ATR=0**: Якщо увімкнено м'який старт (`require_atr=False`), стопи розміщуються на `min_offset` (ефективно 0 дистанції), гарантуючи негайний збиток.
12. **`warmup_full_ready`**: Конкретне визначення "full ready" в Feature Engineering визначає, чи Decision Making взагалі колись почне роботу.
13. **`strategies.aurora` vs `strategies.mean_reversion`**: Окремі секції конфігурації. Конфлікти в карті призначених символів мають вирішуватися через `strategies_registry`.
14. **Ковтання Винятків**: Блоки `try...except Exception` в Обробниках ловлять все, щоб запобігти падінню, але можуть приховувати критичні баги логіки (наприклад, NameError).
15. **Збої Запису WAL**: Якщо дисковий IO для WAL падає, `write_trade_intent_rejected` придушує помилку. Логування зберігається, але в аудиторському сліді можуть бути прогалини.
16. **[RESOLVED] Fail-Open Anti-Pyramiding**: Метод `_handle_flip_orchestration` тепер явно перевіряє стан позиції. Якщо стан "UNKNOWN", повертає помилку `NRR-PORTFOLIO-UNKNOWN` (Fail-Closed). Стара проблема з ковтанням помилок усунена.
17. **[CRITICAL] Hardcoded Anchor**: Символ `BTCUSDT` захардкоджений як якірний актив в `aurora_handler.py`. Це унеможливлює використання стратегії на ринках без USDT або з іншим якорем (ETH).
18. **[HIGH] In-Memory State Loss**: Стани `_pending_flips` та `_qos_state` живуть в пам'яті. Рестарт процесу призводить до втрати контексту "очікування закриття" та скидання лімітів рейт-лімітеру.

## 10) Виправлення та Покращення (Changelog)

**2026-01-27: Critical Fixes Audit**

1.  **[RESOLVED] Silent Liquidity Kappa Gate:**
    -   Раніше: `_check_liquidity_gate` тихо повертав `True` при відсутності фічі (дефолт 0).
    -   Тепер: Викликає `RuntimeError` (Fail-Fast), гарантуючи наявність даних ліквідності перед рішенням.
    
2.  **[RESOLVED] Fail-Open Anti-Pyramiding:**
    -   Раніше: `_has_active_position_same_side` міг приховати помилку `AttributeError` і дозволити відкриття позиції.
    -   Тепер: `_handle_flip_orchestration` повертає `NRR-PORTFOLIO-UNKNOWN` (Fail-Closed), якщо стан позиції неможливо визначити.

3.  **[CONFIRMED] Hardcoded Anchor (Technical Debt):**
    -   Проблема підтверджена: `BTCUSDT` використовується як дефолтний якір. Потребує рефакторингу в майбутньому.

4.  **[CONFIRMED] ATR Zero Fallback (User Risk):**
    -   Проблема підтверджена: При `require_atr=False` стопи ставляться на 1bp. Рекомендовано enforcing `require_atr=True`.
