# Архітектура домену Decision Making

## 1. Патерн Strangler Fig та Декомпозиція
Домен перебуває у стані активної декомпозиції (Phase 14A). Клас `DecisionMaking` у `decision_making.py` тепер є лише "тонким фасадом", який делегує майже всю роботу спеціалізованим компонентам:
- **`IntentBuilder`**: Збірка фінального пейлоаду наміру.
- **`QoSRateControl`**: Керування кулдаунами та лімітами частоти.
- **`ReadinessGates`**: Перевірка TTL фіч та серцебиття (heartbeat) детектора режимів.

## 2. Управління станом (State Management)
Критичний стан домену зберігається в пам'яті (In-Memory), що є архітектурним ризиком:
- `_pending_flips`: Стан незавершених переворотів позицій.
- `_qos_state`: Лічильники лімітів частоти ордерів.
- `symbol_states`: Кеш ознак та результатів останніх розрахунків.

## 3. Модель "Гейтів" (Gating Logic)
Процес прийняття рішення проходить через каскад перевірок:
1. **Timeframe Gate**: Перевірка відповідності `tf_sec`.
2. **Readiness Gate**: Перевірка, чи не застаріли дані (`features_ttl_sec`).
3. **QoS Gate**: Перевірка кулдаунів та рейт-лімітів.
4. **Risk Gate**: Перевірка `risk_score` та `is_trading_allowed`.
5. **Safety Gate**: Перевірка `pm_norm` (волатильності) та `direction_sanity`.

## 4. Оркестрація переворотів (Flip Orchestration)
Домен гарантує безпечний перехід між позиціями (Long <-> Short) через життєвий цикл:
`OPEN_INTENT` -> (якщо протилежна позиція є) -> `CLOSE_INTENT` -> `WAIT_FLAT` -> `OPEN_INTENT`.
Це запобігає "пірамідингу" та забезпечує атомарність зміни напрямку.

## 5. Fail-Closed Design
Система спроектована так, щоб при будь-якій невизначеності (відсутність конфігу, затримка даних ризику, відсутність маржі) — **блокувати** торгівлю.
- Наприклад, якщо `latest_portfolio` не оновлювався довше ніж поріг, сайзинг видасть 0, і намір не буде створено.
