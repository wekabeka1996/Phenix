# Якість коду та технічний борг In-Flight Reconcile

## 1. Ризики та Hotspots
- **Sync Locking**: Хоча `RLock` гарантує безпеку даних, тривале утримання замка при великій кількості ордерів може створювати мікро-затримки для основного потоку FSM при реєстрації нових ордерів.
- **REST API Rate Limits**: Активна звірка великої кількості ордерів через REST API може призвести до перевищення лімітів (IP-ban від біржі).

## 2. Технічний борг (Debt Ledger)

| Елемент | Ризик | Доказ | Рекомендація | Пріоритет |
| :--- | :--- | :--- | :--- | :--- |
| **In-Memory Buffer** | Втрата інформації про завислі ордери при краші системи. | `_entries` у пам'яті | Впровадити збереження стану (SQLite/WAL) для відновлення після рестарту. | High |
| **Linear Search** | Складність $O(N)$ при пошуку прострочених записів. | `get_expired_entries` loop | Використовувати чергу з пріоритетом (Priority Queue) за часом. | Low |

## 3. Рекомендації
- Додати підтримку пакетних (batch) перевірок через `get_open_orders` для всіх символів, щоб зменшити кількість HTTP-запитів.
- Впровадити алертинг у `telemetry`, якщо ордер досягає стану `TTL_EXPIRED`, оскільки це ознака серйозних проблем зі зв'язком.
