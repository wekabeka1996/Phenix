# Архітектура домену In-Flight Reconcile

## 1. TTL-орієнтований менеджмент
Кожен ордер, що реєструється в домені, отримує мітку часу створення.
- **In-flight TTL (60с за замовчуванням)**: Час, після якого система починає активно "підозрювати" ордер у зависанні та ініціює першу REST-звірку.
- **Max TTL (300с за замовчуванням)**: Граничний термін, після якого домен намагається примусово скасувати ордер на біржі та очистити локальний стан у будь-якому випадку.

## 2. Потокобезпека та ізоляція
Реконсилер використовує `threading.RLock` для захисту внутрішнього словника ордерів (`_entries`), що дозволяє безпечно реєструвати нові наміри з різних потоків FSM.

## 3. Модель статусів (InFlightStatus)
Домен оперує розширеним набором статусів:
- `PENDING`: Очікування оновлення.
- `FILLED / CANCELED / REJECTED`: Термінальні статуси, що дозволяють безпечне видалення.
- `NOT_FOUND`: Ордер відсутній на біржі (зазвичай ознака того, що він ніколи не був розміщений).
- `TTL_EXPIRED`: Примусове завершення після таймауту.

## 4. REST Fallback (Truth-Domain Hardening)
На відміну від основного циклу `execution_position`, який покладається на події, цей домен використовує виключно "активний запит істини" через REST API, що є найбільш надійним (хоча і повільним) джерелом даних.
