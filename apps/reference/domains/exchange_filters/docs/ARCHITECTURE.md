# Архітектура домену Exchange Filters

## 1. Принцип Fail-Closed (TASK51-A)
Домен реалізує стратегію жорсткої відмови при невідповідності даних. Це критично, оскільки неправильний `step_size` або `min_qty` призведе до того, що біржа відхилятиме ордери, що може бути катастрофічним під час виконання стратегії.

- **LIVE mode**: Будь-яка критична розбіжність призводить до зупинки (crash) процесу ініціалізації.
- **DEV/SHADOW mode**: Дозволяє продовжувати роботу з попередженням (якщо встановлено прапор `warn_only`).

## 2. Модель даних
Домен використовує два основні контракти:
- **`SSOTFilters`**: Дані, які ми вважаємо істиною в коді (`instruments.yaml`).
- **`ExchangeFilters`**: Реальні дані, отримані з API біржі в реальному часі.

## 3. Пакетна обробка (Performance)
Для прискорення старту (особливо при великій кількості інструментів) валідатор використовує **Batch Fetch** (`get_exchange_info(None)`). Це дозволяє отримати фільтри для всіх символів за один HTTP-запит замість десятків окремих викликів.

## 4. Класифікація розбіжностей (Severity)
Валідатор розумно оцінює ризики:
- **CRITICAL**: Наша конфігурація дозволяє більше, ніж біржа (напр. наш `min_qty` менший за біржовий). Це гарантована помилка при торгівлі.
- **WARNING**: Наша конфігурація суворіша за біржову. Це безпечно, але може бути неоптимально.
