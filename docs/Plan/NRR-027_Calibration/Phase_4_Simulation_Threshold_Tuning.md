# Фаза 4: Симуляція та Тонке Налаштування (Simulation & Threshold Tuning)

## Мета
Застосувати знайдені у Фазі 3 нові математичні пороги до симулятора (Replay Engine) і перевірити їх на "живих" історичних даних. Переконатися, що зміни не ламають інші частини системи (не викликають каскадних відхилень NRR-xxx).

## Джерела даних
*   Оновлені YAML конфігурації (локальні зміни).
*   `data/recorder/` (папки за останні тижні або конкретні дні з високою волатильністю).

## Кроки виконання

1.  **Конфігурація Симулятора:**
    *   Застосувати нові пороги до тестового конфігу (наприклад, `config/aurora/strategies/aurora_test.yaml`).
    *   Встановити симулятор на роботу з даними з `data/recorder` для вибраних тестових днів (наприклад, 30 квітня - 2 травня).
2.  **Запуск Replay (Програвання):**
    *   Запустити конвеєр у режимі `SHADOW` або `BACKTEST` з використанням записаних потоків даних.
    *   Забезпечити запис усіх згенерованих інтентів до тимчасових логів (наприклад, `logs/shadow_nrr027_tuning.jsonl`).
3.  **Валідація Результатів Симуляції:**
    *   Зібрати результати симуляції та порівняти їх з Baseline (Фаза 2).
    *   **Перевірка 1 (Ефективність):** Кількість NRR-027 має зменшитися для False Positives, пропускаючи якісні трейди.
    *   **Перевірка 2 (Безпека):** Угоди, що були пропущені (раніше заблоковані), повинні мати позитивний PnL (чистий прибуток).
    *   **Перевірка 3 (Ізоляція):** Кількість інших реджектів (NRR-062, NRR-026 тощо) не повинна раптово зрости через пропуск неякісних сигналів далі по конвеєру.
4.  **Ітерація (за необхідності):**
    *   Якщо симуляція показує погані результати (наприклад, пропущені трейди виявилися збитковими), повернутися до Фази 3 для перерахунку порогів.

## Очікуваний результат
Звіт про успішну симуляцію (`REPLAY_NRR027_VERIFIED.md`), який підтверджує безпеку та прибутковість нових порогів. Затверджений патч для перенесення конфігів на Production.
