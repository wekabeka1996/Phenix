# Фаза 2: Форензика та Аналіз Базового Стану (Forensic & Baseline Analysis)

## Мета
Зібрати фактичну статистику спрацьовувань NRR-027 у поточній конфігурації системи, щоб зрозуміти масштаб проблеми та ідентифікувати помилкові спрацьовування (False Positives).

## Джерела даних
*   `ops/wal/*.jsonl` (останні дні)
*   `logs/order_log_v1.jsonl`
*   `logs/shadow_critical_event_journal_v1.jsonl`

## Кроки виконання

1.  **Парсинг логів рішень:**
    *   Створити Python-скрипт для читання `order_log_v1.jsonl` та файлів з `ops/wal/`.
    *   Відфільтрувати всі події `DECISION_INTENT_REJECTED`, де `reason` або `nrr_code` дорівнює `NRR-027`.
2.  **Групування та Кластеризація:**
    *   Згрупувати реджекти за `symbol`, `side` (LONG/SHORT) та розпізнаним `regime`.
    *   Витягти з поля `details` або `why_chain` значення сили тренду (trend strength) або confidence, які призвели до блокування.
3.  **Ідентифікація False Positives (Втрачені можливості):**
    *   Співставити таймстемпи відхилених через NRR-027 ордерів з подальшим рухом ціни (використовуючи `logs/features/*.log` або сирі `data/recorder` дані для цих періодів).
    *   Знайти випадки, коли система заблокувала LONG через "DOWNTREND", але ціна відразу після цього пішла вгору (тобто це було дно корекції, а не продовження падіння).
    *   Скласти список "Canary Таймстемпів" — ідеальних точок для тестування нових налаштувань.
4.  **Оцінка Baseline (Базового рівня):**
    *   Зафіксувати поточний відсоток відхилених через NRR-027 угод відносно загальної кількості згенерованих сигналів.
    *   Зафіксувати метрику "Втрачений PnL" (сумарний теоретичний прибуток з угод, які були помилково заблоковані).

## Очікуваний результат
Документ `BASELINE_NRR027_REPORT.md` зі списком проблемних таймстемпів, статистикою блокувань по символах та розрахованим Baseline втраченого прибутку. Ці таймстемпи будуть використані у Фазі 3 та 4.
