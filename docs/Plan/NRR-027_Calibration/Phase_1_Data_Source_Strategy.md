# Фаза 1: Стратегія вибору джерел даних для калібрації NRR-027

## Огляд проблеми NRR-027
NRR-027 (Directional Sanity Block) — це захисний механізм (gate), який відхиляє торгові наміри, якщо напрямок угоди суперечить глобальному тренду (наприклад, блокує LONG під час жорсткого DOWNTREND). Для його калібрації нам потрібно точно визначити, коли тренд дійсно є несприятливим, а коли — це лише короткострокова корекція, яку алгоритм помилково сприймає як зміну режиму.

Найважливіше рішення перед початком калібрації — **на яких даних ми будемо тестувати та оптимізувати пороги?**

## Аналіз доступних джерел даних: За та Проти

### 1. Історичні дані з біржі Binance (Klines / Trades)
Дані, які можна завантажити безпосередньо з API Binance за великий період (роки).

*   **Переваги (За):**
    *   Абсолютна чистота даних.
    *   Можливість перевірки на різних макроекономічних режимах (бичачий ринок 2021, ведмежий 2022, флет 2023 тощо).
    *   Дозволяє провести дуже глибокий бектест.
*   **Недоліки (Проти):**
    *   Це лише "сирі" ціни. Щоб використати їх для NRR-027, нам доведеться проганяти їх через весь наш конвеєр Feature Engineering. Це вимагає значних обчислювальних ресурсів і часу.
    *   Відсутність історичного стану книги ордерів (Order Book) у звичайних Kline даних, що може бути критичним для наших локальних фічей.

### 2. Локальні записи `data/recorder`
Внутрішні "сирі" записи потоків даних системи за останні 3 місяці (лютий - травень 2026).

*   **Переваги (За):**
    *   Точне відтворення того, що бачила система (включаючи Order Book, тіки, об'єми).
    *   Дозволяє ідеальний покроковий replay (симуляцію) з новими налаштуваннями конфігів.
*   **Недоліки (Проти):**
    *   Обмежений горизонт подій (лише 3 місяці).
    *   Потребує часу на програвання (replay).

### 3. Логи ознак `logs/features/*.log`
Величезні файли (по 500-750 МБ на символ), що містять вже розраховані ознаки (features) для кожної мілісекунди.

*   **Переваги (За):**
    *   **Ідеально для швидкого аналізу.** Дані вже оброблені. Ми маємо точні значення `regime_confidence`, трендових індикаторів, волатильності тощо, які подавалися на вхід системі прийняття рішень.
    *   Дозволяє за допомогою скриптів на Python миттєво побудувати гістограми та знайти оптимальні пороги відсікання.
*   **Недоліки (Проти):**
    *   Дані прив'язані до поточної версії генератора фічей. Якщо ми захочемо змінити формулу тренду, ці логи стануть неактуальними.

### 4. Журнали рішень `ops/wal/*.jsonl` та `logs/order_log_v1.jsonl`
Write-Ahead Logs та логи ордерів, де зафіксовані фактичні відхилення по причині NRR-027 у продакшені.

*   **Переваги (За):**
    *   Це фактична правда. Показує, де саме система "помилилася" або "врятувала" нас вчора чи сьогодні.
    *   Містить повний `why_chain` (ланцюжок прийняття рішень).
*   **Недоліки (Проти):**
    *   Тільки постфактум аналіз (що сталося), а не безперервний потік даних. Лише короткий період.

## Висновок та Затверджена Стратегія Даних

Враховуючи необхідність ефективної, швидкої та точної калібрації NRR-027, ми **відмовляємося від масового завантаження нових даних з Binance на перших етапах**. Глибокий бектест (Binance) буде застосований лише у випадку фундаментальної зміни логіки індикатора тренду.

**Поточна стратегія використання даних:**

1.  **Пошук проблемних зон (Forensics):** Використовуємо `ops/wal/*.jsonl` та `logs/order_log_v1.jsonl`. Це дозволить знайти конкретні моменти (таймстемпи), коли NRR-027 спрацював помилково (False Positive) або не спрацював, коли мав би (False Negative).
2.  **Швидка оптимізація порогів (EDA):** Використовуємо `logs/features/*.log`. Ми завантажимо розраховані трендові фічі для знайдених таймстемпів і подивимося на їх розподіл. Це дозволить математично вирахувати нові пороги для "DOWNTREND" та "UPTREND".
3.  **Валідація (Replay):** Після зміни порогів у конфігах (`config/aurora/...`), ми використаємо `data/recorder` для обраних "проблемних" днів (наприклад, 2 травня), щоб провести повну симуляцію (Replay) і підтвердити, що нові пороги пропускають хороші угоди і блокують погані.

Цей підхід мінімізує витрати часу на парсинг сирих даних і максимізує точність завдяки використанню реальних станів системи.
