# Execution / TP-SL / OrderGuardian Architecture Discovery — Round 0

## 1. Вступ
- **Мета:** зафіксувати існуючі факти щодо TP/SL-обробки в execution_position, щоб підготувати платформу до нового Aggregated OCO контракту і рефактору Guardian.
- **Переглянуті модулі:** `apps/reference/domains/execution_position/fsm.py`, `fsm_manage.py`, `order_guardian.py`; `apps/reference/services/order_guardian.py`; `apps/reference/adapters/binance_adapter.py`; `config/aurora/trading.yaml`, `configs/master_config_v1.yaml`; `config_schema_v1.py`; `docs/For_GPT/config_contract_map.md`; `tests/order_guardian/*`.

## 2. Питання 1: Поточна модель TP/SL
- **Відповідь:** система тримає **single OCO** set per entry/symbol when `keep_single_bracket_set=True`. Цей флаг (за замовчуванням `True` в `manage_config.py` та `config_schema_v1.py`) реалізований у `ExecutionPositionFSM` (`fsm.py` рядки ~2287–2314): після placement (`_place_brackets`) через `self.order_guardian.cleanup_other_brackets_for_symbol(...)` гарантується, що лише та пара SL/TP, що повʼязана з поточним `entry_order_id`, залишається. Багатоходова логіка OCO викликає `_register_brackets` → `order_guardian.register_brackets` → `cleanup_other_brackets_for_symbol`, тому multi-bracket behavior (multiple OCO) не підтримується за замовчуванням; system очистить старі набори.

## 3. Питання 2: Кореляція TP/SL ↔ entry
- **Відповідь:** ключове звʼязування відбувається через `parent_entry_id` та `clientOrderId`. `ManageFlowFSM._place_brackets` (fsm_manage.py) реєструє TP/SL, передаючи `entry_order_id` (binance orderId) і генерує власні clientOrderId (`sl_id`, `tp_id`). `OrderGuardian` зберігає як `order:{order_id}` metadata (`parent_entry_id`, `client_order_id`, `reduce_only`, etc.) та при subsequent cleanup порівнює `parent_entry_id` з `keep_parent_order_id`. `clientOrderId` використовується для `guardian_like` перевірок (`_is_guardian_client_order_id`). Отже, саме `parent_entry_id` (entry orderId) є джерелом істини, а `clientOrderId` застосовується для відстеження reducer/close orders та зʼясування, чи належить order до Guardian.

## 4. Питання 3: Підтримка partial-close
- **Відповідь:** `OrderGuardian` підтримує `reduceOnly` orders (apps/reference/services/order_guardian.py рядки ~820–1120) і створює post-fill holds (`_on_order_fill` в fsm.py, рядки ~1030–1080). ManageFlowFSM реагує на `EVENT:ORDER_FILLED` через `_on_order_fill` → `exposure_guard` оновлює позицію, а `cleanup_orphans` запускається (fsm.py рядки ~823–870) лише коли `position_amt` стає 0, інакше пропускається. Partial close (частина qty) не викликає evict—позиція змінюється, але виклик `cleanup_other_brackets` може (через keep_single=true) видалити обидві SL/TP, якщо new entry order реєструється під час fill. Таким чином, partial close зменшує позицію, але графіка OCO не адаптується автоматично, хіба що guardia explicit cleanup вручну. Функція `cleanup_before_close` (рядки ~715–780 services) використовується перед manual close, але не розрізняє partial vs full close.

## 5. Питання 4: Поточний execution mode
- **Відповідь:** config `trading.mode` (config/aurora/trading.yaml) встановлено як `shadow_live` з модульними режимами (`execution_position.trading_mode="testnet"`). У `risk`/`decision` (`trading.yaml` секція execution/exposure) є long/short-настройки, exposure guard не фільтрує short; `manage_flow` не обмежує direction. У `config` немає `long_only` або `short_only` прапорів, `order_guardian` оперує з обома side. На adapter рівні Binance futures підтримує двосторонній режим — reduceOnly flags ставляться залежно від `side`. Отже, execution mode — **full hedge (двосторонній)** (config дозволяє BUY/SELL, exposure guard має per-side caps).

## 6. Питання 5: Кількість дозволених OCO-наборів
- **Відповідь:** `keep_single_bracket_set` (manage_config, config_schema) контролює: якщо `True`, guard викликає `cleanup_other_brackets_for_symbol` після реєстрації нової entry, видаляючи всі чужі набори (см. fsm.py рядки ~2293 та services/order_guardian cleanup). `OrderGuardian` також скасовує `reduceOnly`/`closePosition` ордери, які не мають metadata matching `parent_entry_id`. Таким чином, лише **один активний OCO** допускається при дефолтному конфігу; механізм scale-in не підтримує кілька OCO, поки флаг не відключено. Batch cleanup (config `guardian.batch_limit`) скасовує все, що не match entry.

## 7. Питання 6: Точка створення TP/SL
- **Відповідь:** TP/SL створюються у `ManageFlowFSM._place_brackets` (apps/reference/domains/execution_position/fsm_manage.py, рядки ~282–520). Ланцюг: `EVENT:ORDER_PLACED` або `ORDER_FILLED` → `ExecutionPositionFSM` просуває `manage_flow` для символу → `_place_brackets` викликає `brackets_config.calculate` / `TP/SL validation` → `decide` відправляє `DEC:PLACE_ORDER` → адаптер (`apps/reference/adapters/binance_adapter.py` з `place_bracket_order`/`place_order`) посилає запити з `reduceOnly` flag. Після відповіді `OrderGuardian.register_brackets` ставить `parent_entry_id` і `clientOrderId`, а FSM зберігає `sl_order_id`, `tp_order_id`. Таким чином ланцюг: EVENT → ManageFlowFSM `_place_brackets` → `brackets_config` (склад TPs/SLs) → Binance adapter `place_order` → response.  

## 8. Загальний звіт про стан Execution/TP-SL Pipeline
- Current pipeline налаштований на **single OCO per entry**, керований `keep_single_bracket_set`. OrderGuardian робить cleanup based on `parent_entry_id`, `reduceOnly`, `closePosition`, та `cleanup_other_brackets`. FSM викликає cleanup одразу після Registration і під час periodic loops. Partial/scale-in дії можуть ненавмисно "знищити" нові TP/SL через агресивні cleanup-цикли і федераль "keep single" policy. Legacy/Deprecated: `config.manage.bracket.keep_single` флаг незмінно true; `atomic_close`/`orphan_monitor` настроюють cleanup policy. Найризиковішими місцями є `ManageFlowFSM._place_brackets` (cleanup після registration) та `OrderGuardian.cleanup_other_brackets_for_symbol` (вимітає інші entry без агрегування).

## 9. Рекомендації перед проектуванням Aggregated OCO
1. Увімкнути `keep_single_bracket_set=False` або відкласти `cleanup_other_brackets_for_symbol` до моменту, коли нові TP/SL підтверджені (ACK/FILL) — інакше scale-in постійно очищатиме нові ордери.  
2. Розширити metadata (зберігати `entry_uuid`, `clientOrderId`, `parent_entry_id`, `order_id`) і використовувати його в `cleanup_other_brackets` для агрегації, а не простого cancel.  
3. Додати `cleanup_on_scale_in` (config flag) та (`reduceOnly`/`closePosition`) guards, щоб уникнути premature cancels при partial fills.  
4. Заменити `cleanup_orphans` і `cleanup_other_brackets` на агрегатний воркфлоу, який не скасовує TP/SL нового entry без перевірки position size та `reduceOnly`.  
5. Документувати параметри guardian/connector (`guardian.cleanup_ttl_ms`, `execution.allow_trade_with_guardian_tidy_only`, `orphan_monitor`) як частину нового Aggregated OCO контракту.  
6. Створити тест, що симулює множественный entry і scale-in, щоб спостерігати, як cleanup реагує, та перенести флаг `keep_single_bracket_set` до `decision.manage` як реальне налаштування.
