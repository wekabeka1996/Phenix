# Aurora Phase 9 — Quadratic Brain (LIVE Trading)

**Технічна концепція / інженерний документ (SSOT, fail-closed, без тихих фолбеків)** 

---

## 0) Мета

Побудувати production-ready LIVE ядро прийняття рішень **Quadratic Brain**, яке:

1. Перетворює **впевненість** (confidence) у **експозицію/ризик** (exposure) через квадратичне ядро.
2. Має **Defense Layer** (Shields), які **тільки зменшують** ризик (multiplier ≤ 1.0).
3. Має **жорсткі протоколи входу/виходу** та дисципліну позицій.
4. Працює на **5m basis bars** (або інший basis TF), але використовує **multi-TF Pillars** (M15/H4/D1) як “мозок контексту”.
5. У LIVE не чекає «200 днів прогріву», а робить **startup warmup/backfill** через завантаження історичних свічок і прогін через FE (Feature Engineering).
6. Немає «двох правд»: **SSOT для pillar_sum — тільки FE**. Будь-які деградації — **explicit**, під feature-flag, з reason_code і risk-cap.

---

## 1) Визначення (коротко, щоб ми говорили однаково)

* **Basis timeframe (basis TF)**: основний таймфрейм, на якому працює стратегія/ішення (типово 5m).
* **Pillars**: 3 мульти-TF компоненти контексту:

  * **Tactician (M15)** — тактичний імпульс (ROC/подібне).
  * **Operator (H4)** — робочий вектор (LinReg slope + ADX/подібне).
  * **Strategist (D1)** — “територія” (ціна відносно SMA(200)).
* **pillar_sum**: агрегований (зважений) лінійний сигнал від трьох Pillars, SSOT = FE.
* **Quadratic transform**: `conf = sign(s) * s²` (після clamp/нормалізації).
* **Shield**: функція, що дає multiplier ∈ [0..1], **ніколи** не збільшує ризик.
* **Fail-closed**: якщо критичні дані/контракти відсутні або неготові — **не торгувати**, а не “якось” торгувати.

## 2) High-Level Архітектура (LIVE)

### 2.1 Потоки даних

**A. Market Data → Bar Aggregation**

* Вхід: тики/клайни/стрім.
* Вихід: bar close події для `basis TF` + агреговані бари для M15/H4/D1 (як мінімум для Pillars).
* SSOT time: **bar_close_ts** (секунди) — використовується скрізь (TTL, MemoryShield dedup, deterministic behavior).

**B. Feature Engineering (FE)**

* На кожному барі відповідного TF:

  * оновлює буфери OHLC/індикаторів для Pillars,
  * обчислює `pillar_tactician/operator/strategist`,
  * обчислює `pillar_sum` і `pillar_contribs`,
  * емітить features в шину.

**C. Decision Making**

* `QuadraticScoringKernel` бере **pillar_sum (SSOT)** і робить quadratic confidence.
* `ShieldCascade` застосовує ContextShield → MemoryShield → DangerZoneShield → …
* `ExecutionGate` вирішує: EXECUTE / IGNORE / WAIT / REJECT.
* `EntryPlan` / `ExitManager` формують TP/SL/Trailing правила.
* `InstrumentQuantizer` переводить raw exposure/qty в біржеві constraints.
* Далі створюється `TRADE_INTENT_PROPOSED` → домен виконання/ордерів.

## 3) LIVE Warmup / Backfill (ключова ідея: “без реального вармапу”)

### 3.1 Чому це потрібно

Strategist D1 SMA(200) не прогріється “в реальному часі” без 200 днів D1 барів. У LIVE це неприйнятно.
Отже, **перед стартом торгівлі** ми:

1. **Завантажуємо історичні свічки** потрібних TF (M15/H4/D1 або basis→resample) на потрібну глибину.
2. **Проганяємо ці свічки через FE**, щоб заповнити буфери/індикатори.
3. Лише після “READY” дозволяємо торгові рішення.

### 3.2 Warmup Manager (концепт)

**Компонент:** `WarmupManager` (або `PillarBackfillService` + `WarmupRunner` як одна підсистема).
**Задача:** забезпечити readiness Pillars + стабільний контракт даних.

**Алгоритм LIVE старту:**

1. `preflight_config_validate()` — Pydantic strict `extra="forbid"`, всі risk-критичні секції або присутні, або система fail-closed (наприклад, ExitManager).
2. `warmup_plan = compute_lookback()`:

   * tactician: `M15_bars_needed`
   * operator: `H4_bars_needed`
   * strategist: `D1_bars_needed` (типово SMA200 → 200 D1)
   * додаємо `buffer_ratio` (наприклад 5–10%) **конфігом**, не хардкод.
3. `fetch_candles()`:

   * джерело: біржа (REST) або локальний кеш (якщо є).
   * TF: D1/H4/M15 (або basis 5m і ресемпл у BarAggregator — але для D1/H4 в LIVE часто дешевше/надійніше брати нативні D1/H4).
4. `replay_into_FE()`:

   * подати свічки у FE в правильному порядку часу,
   * `emit_events=False` на фазі warmup (ніяких STRATEGY_SIGNAL),
   * оновити всі буфери, щоб `pillar_*` і `pillar_sum` стали READY.
5. `warmup_readiness_check()`:

   * якщо `strict_ready=true` і будь-який pillar не READY → **abort start** (fail-closed) з чітким reason_code (наприклад `WARMUP_NOT_READY:strategist_missing_200_d1`).
6. Увімкнути normal runtime: `emit_events=True`, `decision_enabled=True`.

### 3.3 Немає тихих фолбеків

* Якщо warmup вимкнено, або дані не завантажились, або readiness не досягнуто — **торгівля не стартує** (або стартує в “disabled decisions” режимі з явним WARN+reason, залежно від config).
* Будь-який “degraded mode” дозволяється **тільки** якщо він явно увімкнений в конфігу, має власні reason_codes і risk caps (див. розділ 9).

## 4) Pillars (SSOT і контракти)

### 4.1 Підсумок

* FE — єдине місце, де рахується `pillar_sum`.
* Decision домен **не перераховує** `pillar_sum` ніякими іншими фічами (OBI, delta_price тощо). Це інша “математика”, і це створює дві правди.

### 4.2 Контракт FE → Decision

FE має емісити (коли READY):

* `pillar_tactician`, `pillar_operator`, `pillar_strategist` (нормалізовані у [-1..1])
* `pillar_sum` (лінійна зважена сума Pillars)
* `pillar_contribs` (debug/xai: внесок кожного pillar)
* `bar_close_ts` (SSOT time)
* `regime` і `regime_ts_ms` (якщо режимний детектор у системі)

Якщо не READY:

* `pillar_sum = None` (або відсутній ключ)
* FE може емісити `pillar_ready_flags` або мінімум debug-метрики, але рішення має **fail-closed**.

## 5) Quadratic Scoring Kernel

### 5.1 Формула

1. Вхід: `pillar_sum = s` (очікуємо нормалізований діапазон ~[-1..1]).
2. Safety clamp: `s_clamped = clamp(s, -1, 1)` — щоб не допустити розліт експозиції через помилки.
3. Quadratic: `confidence = sign(s_clamped) * (s_clamped ** 2)`.

### 5.2 Пороги і плавність

* Пороги (signal_threshold, regime_threshold_multipliers тощо) — **конфіг**, не код.
* Якщо threshold занижений — отримаєш більше трейдів, але на шумі. Якщо завищений — менше трейдів, але якісніші. Це і є “ручка” тюнінгу.

### 5.3 Fallback on error

* `fallback_on_error: legacy` — дозволено, але:

  * fallback **явний**, логований (reason_code типу `KERNEL_EXCEPTION_FALLBACK_LEGACY`),
  * не “перемикаємося назавжди” без явного рішення; fallback може бути per-call.

## 6) Shields (Defense Layer, multiplier-only)

### 6.1 Загальні правила

* Shield повертає `ShieldResult(multiplier, reasons[], details{})`.
* `multiplier ∈ [0..1]`. >1 заборонено контрактом.
* `evaluate()` — pure read (ніяких записів/IO). Запис стану — окремим викликом (наприклад `record_visit()`), який викликається **тільки** в контрольованих місцях (наприклад після “signal produced”).
* Нема “тихих” дефолтів: якщо щиту потрібні ключі, а їх нема — він повертає детермінований результат + reason_code (`MISSING_FEATURES:[...]`).

### 6.2 ContextShield (Regime + TTL)

* Джерела: `features["regime"]`, `features["regime_ts_ms"]`, `features["bar_close_ts"]`.
* TTL логіка: якщо режим застарів (`bar_close_ts` – `regime_ts_ms` > ttl) → multiplier знижується:

  * normal stale → `stale_mult_normal`
  * danger stale → `stale_mult_danger`
* Danger regime визначається через allow-list/regex у конфігу (UPPERCASE режими).

### 6.3 MemoryShield (пам’ять станів)

* Coarse state hashing (≈ 50–60 станів), decay, LRU cap.
* Persistence policy:

  * `storage_path=None` → RAM-only (типово для тестів/беків).
  * `storage_path=/path` → LIVE persistence з atomic write, throttling, `flush()` на shutdown.
* Навчання:

  * `record_visit(state, bar_ts)` викликається **тільки** після того, як пройшли гейти і ми реально емітимо intent/сигнал (тобто “візит” = реальна дія/вихід у виконання, а не CPU-цикли).

### 6.4 DangerZoneShield (аварійна зона)

* Визначає аварійні умови (vol/spread/motion/ATR-аномалії — як у конфігу).
* Reason contract: **канонічний префікс** `DANGER_ZONE:`.
* Взаємодія з ExitManager:

  * DZ може давати `CLOSE_POSITION` або `TIGHTEN_STOPS`.
  * Tighten лише при **PnL > 0** (щоб не прискорювати збиток).

## 7) Money Management + Quantization

### 7.1 Sizing

* Формула risk-based або інша стратегія sizing — але все конфіг-кероване.
* Вихід sizing: raw notional/qty (Decimal).

### 7.2 InstrumentQuantizer (обов’язковий крок перед біржею)

* Приймає raw qty + price + instrument constraints (min_qty, step_size, min_notional, tick_size).
* Вихід:

  * або `QuantizedResult` (qty округлено вниз/до кроку),
  * або REJECT з reason_code `QUANTIZER_REJECT:<reason>` (fail-closed).

## 8) Execution Protocols

### 8.1 ExecutionGate (стадії)

Протокол на рівні рішення (не на рівні біржі):

1. Hard veto (Context HIGH / Danger активний / інші критичні умови) → REJECT.
2. Conflict check (наприклад, strategist проти входу) → WAIT/IGNORE залежно від сценарію.
3. Soft threshold (|score| нижче порогу) → IGNORE.
4. Execute → пропонуємо intent.

Кожна стадія має `enabled` toggle + стандартизований reason_code.

### 8.2 EntryPlan

* Стандартний вхід і Knife-сценарій (якщо потрібно).
* Для Knife — окремі правила, зменшений size multiplier, підтвердження follow-through.

### 8.3 ExitManager (централізовано)

Пріоритети (концептуально):

1. Danger CLOSE_POSITION
2. Danger TIGHTEN_STOPS (тільки в прибутку)
3. Trailing Stop
4. Time expiry
5. Signal reversal / інші м’які умови

Trailing (ATR-based) потребує MFE tracking у SymbolState (highest/lowest favorable price) і ATR.

## 9) Degraded Mode (опціонально, але тільки explicit)

Якщо бізнес-вимога: “торгувати ДО прогріву D1 SMA200”, це робиться **не підміною SSOT**, а **контрактною деградацією**:

* `scoring_engine.degraded_mode.enabled: false` (default).
* Якщо `pillar_sum missing` і degraded_mode увімкнено:

  * kernel використовує альтернативний сигнал **з явним маркером**:

    * `scoring_source=DEGRADED_LINEAR`
    * `reason=DEGRADED_PILLAR_WARMUP`
  * жорсткий risk-cap: наприклад max exposure multiplier ≤ 0.2, або підвищений threshold, або тільки “reduce-only” режим.
* Якщо degraded_mode вимкнено → `defer_reason=PILLAR_WARMUP` (fail-closed).

Це важливо: **ніяких тихих фолбеків** і **ніяких “магічних чисел”** — все параметризовано в YAML/Pydantic.

## 10) Конфігурація і валідація

### 10.1 Pydantic strict

* `extra="forbid"` на всіх моделях Phase 9.
* Жодних “fallback to defaults silently” для risk-критичних блоків. Приклад політики:

  * ExitManager секція відсутня → або `ConfigContractError` (strict), або явне `exit_manager=None` з WARN і disabled (але це має бути **конфіг-керований режим**, не мовчазний).

### 10.2 Toggles

Кожен механізм обмеження/захисту має `enabled: bool`:

* scoring engine selection
* shields master + per-shield
* execution gate stage toggles
* entry scenarios toggles
* exit scenarios toggles
* quantizer on/off (але в live бажано never off)

## 11) Observability / Forensics

### 11.1 Contract-first reason codes

Кожен блок/ігнор/вейт має:

* reason_code (стабільний, машинно-читаний)
* details (ключові числові поля для дебагу)

### 11.2 Логи, WAL, метрики

* WAL/журнали не повинні блокувати старт live (ініціалізація має бути bounded).
* Метрики:

  * кількість `PILLAR_WARMUP` defers
  * частота DZ triggers
  * memory coverage (скільки станів Known/Exploring/Unknown)
  * distribution score до/після shields
  * reject причини quantizer/exec gate

---

## 12) Failure Modes (що робимо коли все пішло не так)

* Нема історичних свічок для warmup → fail-closed (не стартуємо decisions).
* RegimeDetector завис → TTL stale зменшує ризик.
* Shield missing features → детерміноване зниження multiplier + reason.
* Kernel exception → fallback_on_error (explicit) або fail-closed.
* Quantizer не може зібрати валідний qty → REJECT (fail-closed), не “пробуємо якось”.

---

## 13) Rollout (LIVE)

1. Dry-run режим (testnet/hybrid):

   * warmup + readiness gate включені
   * execution може бути testnet, data реальні
2. Увімкнути quadratic engine + shields з conservative thresholds
3. Спостерігати метрики coverage/reasons 1–3 дні
4. Поступово тюнити **конфігом**: thresholds, regime multipliers, shield multipliers
5. Будь-яке “degraded mode” — тільки якщо є чітка бізнес-причина і risk-caps.

---

## 14) Підсумок концепції (в одному абзаці)

LIVE Quadratic Brain — це pipeline, де **FE є SSOT для pillar_sum**, а система стартує з **історичним warmup/backfill** (M15/H4/D1) щоб Pillars були READY до першого рішення; QuadraticKernel робить `sign(s)*s²` зі safety clamp, Shields каскадно **лише зменшують** ризик (Context TTL + Memory state + DangerZone), ExecutionGate/EntryPlan/ExitManager задають дисципліну, InstrumentQuantizer гарантує біржеву валідність; уся поведінка керується **строгими Pydantic-конфігами без тихих фолбеків**, з reason_codes і повною спостережуваністю.
