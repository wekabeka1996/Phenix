# DISC-01 Position State

## Джерела позицій (WS/REST/ledger)
- `AccountObserver` polls Binance via `python-binance`, deduplicates trade IDs, and emits `EVT:TRADE_EXECUTED` (and legacy `EVT:FILL`) every `poll_interval` seconds, so this is the closest thing to an exchange WS feed in the current stack (`apps/reference/domains/account_observer/account_observer.py:205`, `:275`).
- `AccountConnector` drives the REST snapshot side: its `_monitor_loop` wakes every `poll_interval` (default 30 s) to call `BinanceAdapter.get_account_balance` and `get_open_positions` (which hits `/fapi/v2/positionRisk` and returns normalized `ExchangePosition` objects like `vfoundation/core/adapters/base.py:68` and `apps/reference/adapters/binance_adapter.py:539`). It emits `EVT:ACCOUNT_UPDATE_RECEIVED` with `positionAmt`, `entryPrice`, `markPrice` and also exposes `force_snapshot_refresh` hooks for manual resyncs (`apps/reference/domains/account_balance/account_connector.py:129`, `:143`, `:229`, `:281`).
- `OrderTimeoutWatchdog` keeps a REST poller for missed fills: `set_hooks` wires in `get_order`/`emit_fn`, a global 10 RPS throttle guards `_watchdog_loop`, and filled/cancelled orders are forwarded as `EVT:TRADE_EXECUTED`/`EVT:ORDER_STATE_CHANGED` when the WS path is silent (`apps/reference/domains/execution_position/watchdog.py:79`, `:87`, `:303`, `:339`).
- `PositionTracking` is the internal ledger and the “ground truth” downstream domains read from. It WAL-appends every processed `EVT:TRADE_EXECUTED`/`EVT:ACCOUNT_UPDATE_RECEIVED`, stores `symbol -> {quantity, avg_price, venues}`, and emits `EVT:PORTFOLIO_STATE_UPDATED` for downstream consumers (`apps/reference/domains/position_tracking/position_tracking.py:358`, `:599`, `:706`, `:412`, `:1283`). Manual `CMD:POSITION_FORCE_RESYNC` is also supported by wiring a `snapshot_fetcher` (see `apps/reference/main.py:779`, `:1001`) that calls `AccountConnector.force_snapshot_refresh` and replays the resulting payload (`apps/reference/domains/position_tracking/position_tracking.py:1314`, `:1321`).
- `ExecPosFSM` keeps a lightweight `PositionSnapshot` cache fed from every portfolio update and fill event; `_ingest_ws_positions`/`_ingest_ws_fill_payload` keep `self._ws_position_cache` in sync so `_preflight_position_check` can make fast, WS-first decisions (`apps/reference/domains/execution_position/fsm.py:76`, `:599`, `:611`, `:3456`). When the cache is stale (>1.5 s by default) it falls back to the `get_open_positions` REST call, stores the result in the same cache, and only then allows bracket placement (`apps/reference/domains/execution_position/fsm.py:215`, `:3465`-`:3498`).

## Потоки оновлення позицій (коли й що викликається)
- `AccountObserver`/`OrderTimeoutWatchdog` → `EVT:TRADE_EXECUTED` → `PositionTracking.on_trade_executed` updates quantity/avg price, calls `_update_position`, recalculates realized PnL, and emits `EVT:PORTFOLIO_STATE_UPDATED` containing `_get_positions_snapshot()` data (`apps/reference/domains/account_observer/account_observer.py:205`, `:275`; `apps/reference/domains/position_tracking/position_tracking.py:599`, `:1022`, `:1283`, `:698`).
- The balance/positions REST snapshot emitted by `AccountConnector._emit_positions_update` (`apps/reference/domains/account_balance/account_connector.py:337`) is consumed by `PositionTracking.on_account_update` to reconcile with the ledger, log drift metrics (`snapshot_reconciliation_drift_total`, `inc_position_sync_drift_total`), detect manual closes, and emit another `EVT:PORTFOLIO_STATE_UPDATED` for the latest account state (`apps/reference/domains/position_tracking/position_tracking.py:706`-`:814`).
- Every portfolio update lands in `ExecPosFSM._on_portfolio_state_updated`: the raw payload is stored as `_latest_portfolio_state`, `self._ingest_ws_positions` keeps `PositionSnapshot`s for fast gating, `order_guardian.reconcile_symbol` is invoked when amounts go to zero, and `exposure_guard`/`postfill_reservations` are refreshed before emitting the aggregated exposure summary (`apps/reference/domains/execution_position/fsm.py:1186`-`:1312`).
- Before placing TP/SL the manage flow awaits `_preflight_position_check`, which prefers WS cache but, on cache miss/stale data, blocks until a REST `get_open_positions` snapshot arrives; the snapshot is cached and used for the remainder of the decision (`apps/reference/domains/execution_position/fsm.py:3456`-`:3489`). This ensures `_preflight_position_check` is the gate that can stall bracket placement while it waits for the latest confirmed position.
- `PositionTracking.register_snapshot_fetcher` points to `AccountConnector.force_snapshot_refresh`, so the `CMD:POSITION_FORCE_RESYNC` path forces a synchronous REST round-trip, logs the operation, and emits `EVT:POSITION_FORCE_RESYNC_COMPLETED` once a fresh snapshot arrives (`apps/reference/domains/position_tracking/position_tracking.py:1314`, `:1321`, `:1363`).

## Поведінка при частковому закритті
- On every fill `PositionTracking._update_position` computes how much quantity is being reduced, adjusts realized PnL, updates quantity/average price (resetting the avg if the side flips), and re-emits the portfolio snapshot, so the internal ledger always trails the executed trades (`apps/reference/domains/position_tracking/position_tracking.py:1022`).
- The same fill feeds `ExecPosFSM._on_trade_executed`, which drives `exposure_guard.on_fill`, notifies `OrderGuardian`, and later lets `_on_portfolio_state_updated` refresh the WS cache from the new `positions` array before any conditional orders are touched (`apps/reference/domains/execution_position/fsm.py:1391`-`:1458`, `:1186`-`:1312`).
- Partial closes therefore update both the ledger quantity and the cached `PositionSnapshot` sitting behind `_preflight_position_check`, with realized PnL updated and new portfolio payloads emitted immediately so downstream components see the reduced size.

## Поведінка при повному закритті
- When `/positionRisk` shows `positionAmt == 0`, `_reconcile_positions_from_snapshot` removes the symbol from `_positions`, flags the tuple in `manual_closes`, and the code path notifies `AlertManager` about the manual intervention before emitting the new portfolio snapshot (`apps/reference/domains/position_tracking/position_tracking.py:412`-`:814`).
- `ExecPosFSM._on_portfolio_state_updated` notices that the incoming `positions` array reports a zero for a previously tracked symbol, logs `[POSITION_CLOSED]`, and immediately calls `order_guardian.reconcile_symbol` to cancel lingering reduce-only/closePosition orders tied to that side (`apps/reference/domains/execution_position/fsm.py:1186`-`:1315`).
- Because `_get_positions_snapshot` filters out zero-quantity entries, future portfolio payloads omit the symbol until a new position opens (`apps/reference/domains/position_tracking/position_tracking.py:1283`).

## Поведінка при рестарті / DR
- `PositionTracking` WAL-logs every trade/account event (`_append_event_to_wal`), respects `strict_wal` from `[trading.dr|dr|system.dr]`, and exposes `get_snapshot()` plus `force_full_resync()` so the ledger can be rebuilt or externally validated (`apps/reference/domains/position_tracking/position_tracking.py:98`, `:130`, `:358`, `:1392`).
- During startup the `position_tracking` domain sticks a `snapshot_fetcher` hook onto `AccountConnector.force_snapshot_refresh`, so `CMD:POSITION_FORCE_RESYNC` immediately triggers a synchronous REST poll that helps the ledger restart from a known account snapshot (`apps/reference/main.py:779`, `:1001`; `apps/reference/domains/position_tracking/position_tracking.py:1314`, `:1321`).
- `ExecPosFSM` records every incoming message (`msg_in`) and decision (`msg_out`) into `vfoundation.dr.wal`, and `replay_on_startup()` can replay those logged messages to rebuild flow state before execution continues (`apps/reference/domains/execution_position/fsm.py:1965`-`:2096`).
- `AccountConnector`’s background thread/`force_snapshot_refresh` ensure that even after crash/restart the wallets and positions are polled, and any manual resync route takes a new `AccountConnector` fetch instead of reusing stale cache (`apps/reference/domains/account_balance/account_connector.py:129`-`:149`, `:281`).

## Потенційні вікна розсинхрону (ризики)
- `ExecPosFSM` considers WS snapshots stale after `positions.ws_snapshot.max_age_ms` (1.5 s default) and falls back to REST `get_open_positions`, so the manage flow can block for a few hundred milliseconds while waiting for Binance to respond (`apps/reference/domains/execution_position/fsm.py:215`, `:3456`-`:3489`).
- `AccountConnector` only polls balances/positions every ~30 s by default, which means the ledger relies on trade events to stay current between snapshots; if trades/WS messages stop, the next `EVT:ACCOUNT_UPDATE_RECEIVED` (and thus `_reconcile_positions_from_snapshot`) can lag for 30 s (`apps/reference/domains/account_balance/account_connector.py:50`-`:55`, `:143`).
- `OrderTimeoutWatchdog`’s REST fallback is voluntarily throttled to 10 RPS and builds an exponential backoff per order, so fills detected via polling can take seconds to surface if the WS stream disappears (`apps/reference/domains/execution_position/watchdog.py:79`, `:97`, `:303`).
- `_reconcile_positions_from_snapshot` keeps drift counters and fires `AlertManager` for manual closes, which is the signal that the internal ledger already saw a position that no longer exists on the account; the presence of those alerts is itself evidence of a de-synch window that was later closed (`apps/reference/domains/position_tracking/position_tracking.py:412`-`:814`).
- The REST position payload emitted by `AccountConnector` skips `positionAmt == 0` entries and logs `FALLBACK_TRIGGER` when Binance answers with an empty list, so there is a brief period where the system uses its internal `self._positions` to compute exposures until the next successful snapshot (`apps/reference/domains/account_balance/account_connector.py:221`, `:337`).
