# Глибокий звіт: Аналіз червоних тестів системи (Timeout & Execution)

**Дата виконання:** 24 лютого 2026 р.
**Об'єкт аналізу:** 5 тестів, які стабільно падають (pre-existing failures) під час виконання `pytest`.

Цей звіт містить глибокий розбір причин падіння тестів. Завдання — з'ясувати, чи ці падіння є симптомами реальних багів у бізнес-логіці, чи це просто застарілий тестовий код (test debt), який не встигає за рефакторингом.

---

## 1. `test_decision_clock_one_cmd_per_bar`
**Файл:** `tests/backtest_engine/test_decision_clock_guard.py`
**Помилка:** `AttributeError: 'BacktestEngine' object has no attribute '_bar_closed_count'`

### 🔍 Глибокий аналіз
Цей тест намагається перевірити, що рушій бектесту (Backtest Engine) обробляє по одному `CMD:PROCESS_STRATEGY` на кожен закритий бар (Bar). Для цього він напряму звертається до приватної змінної `engine._bar_closed_count`. 
Проте, під час нещодавнього рефакторингу логіки бектесту (або інтеграції `BarAggregator`), ця змінна була видалена або перенесена в інший компонент (наприклад, у спеціалізований лічильник метрик). 
**Висновок:** Це **Legacy Test (Тестовий борг)**. Продакшн-код працює (симуляція проходить успішно, як видно з логів: `Simulation ended. Processed 12 bars`), але тест жорстко прив'язаний до застарілої внутрішньої імплементації (private attributes).

## 2. `test_decision_clock_duplicate_cmd_raises`
**Файл:** `tests/backtest_engine/test_decision_clock_guard.py`
**Помилка:** `Failed: DID NOT RAISE <class 'RuntimeError'>`

### 🔍 Глибокий аналіз
Тест симулює ситуацію "подвійного" надсилання команди `CMD:PROCESS_STRATEGY` на одному й тому ж барі і очікує, що рушій бектесту "впаде" з помилкою `RuntimeError("double decision clock")`.
Але помилки не відбувається. Це свідчить про те, що архітектура системи змінилася. Очевидно, зараз бектест-рушій (або сам FSM) використовує **idempotency checks** (перевірки на ідемпотентність) або `BoundedEventDeduper`, які просто тихо ігнорують дубльовані команди (повертаючи no-op), замість того, щоб падати (Crash).
**Висновок:** Це **Legacy Test**. Тест відображає застарілу вимогу "падати при дублікатах", тоді як поточна система коректно (і безпечніше) дедуплікує їх. Тест потрібно переписати на перевірку того, що друга команда була проігнорована (наприклад, через перевірку лічильника оброблених команд).

## 3. `test_extract_backtest_config_snapshot_includes_repro_anchors`
**Файл:** `tests/backtest_engine/test_reporting_config_snapshot.py`
**Помилка:** `assert False` (через те, що генератор `any()` не знайшов потрібного шляху)

### 🔍 Глибокий аналіз
Тест перевіряє, що функція створення снепшоту конфігурації для бектесту (`_extract_backtest_config_snapshot`) включає хеші основних SSOT-файлів, зокрема `config/aurora/regime.yaml`. Проте `paths` не містить цього файла.
Це може бути наслідком того, що файли конфігурації були переміщені, перейменовані, або ж логіка `_extract_backtest_config_snapshot` більше не відстежує цей файл через нову ієрархію Pydantic-моделей.
**Висновок:** Це **Integration Drift (Розсинхронізація інтеграції)**. Тест не встиг за змінами структури папок конфігурацій (SSOT) або механізму трекінгу файлів.

## 4. `test_fields_load_and_reach_runtime`
**Файл:** `tests/config/test_btcusdt_aurora_runtime_fields.py`
**Помилка:** `AttributeError: 'types.SimpleNamespace' object has no attribute 'shield_multiplier'`

### 🔍 Глибокий аналіз
У цьому тесті використовується кастомний об'єкт-заглушка (`_SpyKernel`), який замінює реальний скоринговий рушій (Scoring Kernel) і повертає `SimpleNamespace` із тестовими даними. 
У логах видно повідомлення: `Phase 9: QuadraticScoringKernel activated with NullShield()`. Тобто бізнес-логіка була оновлена для роботи зі "Щитами" (Shields). Відповідно, метод `_process_decision` в `AuroraHandler` тепер очікує, що результат скорингу міститиме атрибут `shield_multiplier`. Але мок-об'єкт `_SpyKernel` у тесті не був оновлений і не має цього атрибута.
**Висновок:** Це **Mock Rot (Гниття моків)**. Чистий тестовий борг. Продакшн-код очікує нове поле, а тестовий мок його не надає. Потрібно додати `shield_multiplier=1.0` до `SimpleNamespace` у тесті.

## 5. `test_regime_sizing_reaches_decision_making`
**Файл:** `tests/config/test_btcusdt_aurora_runtime_fields.py`
**Помилка:** `AttributeError: property 'latest_portfolio' of 'DecisionMaking' object has no setter`

### 🔍 Глибокий аналіз
Тест намагається брутально змінити стан домену, привласнюючи значення: `dm.latest_portfolio = {"equity": "1000"}`.
Однак в процесі посилення інкапсуляції (скоріш за все, під час недавніх рефакторингів `DecisionMaking`), поле `latest_portfolio` було перетворено на **read-only property** (властивість без сеттера), щоб запобігти зовнішній мутації стану (Fail-Closed Data Integrity). Стан портфеля тепер має оновлюватися виключно через обробку FSM-подій (наприклад, `EVT:PORTFOLIO_STATE_UPDATED`).
**Висновок:** Це **Encapsulation Violation (Порушення інкапсуляції в тесті)**. Тест робить те, що продакшн-коду робити суворо заборонено. Тест необхідно змінити: замість прямого присвоєння слід передавати подію через метод-обробник або створювати об'єкт із правильним початковим станом через конструктор.

## 🎯 Загальний підсумок (Executive Summary)

Усі 5 червоних тестів **НЕ є критичними багами** продакшн-системи. Жоден з них не свідчить про поломку торговельної логіки, ризик-менеджменту чи втрати даних.

Це класичний **Технічний Тестовий Борг (Test Debt)**, який виник через те, що тести надто сильно "зрослися" із внутрішньою реалізацією класів (White-box testing):
1. Пряме читання приватних лічильників (`_bar_closed_count`).
2. Очікування винятків замість перевірки ідемпотентності.
3. Застарілі mock-об'єкти, які не мають нових полів (`shield_multiplier`).
4. Спроби прямого запису в read-only властивості (`latest_portfolio`).

**План дій (Actionable Fixes):**
Ці тести можна полагодити за 10 хвилин, оновивши їх відповідно до нових контрактів класів (додати потрібні атрибути до моків, змінити логіку assert'ів, не записувати в properties). Це не вимагає втручання в архітектуру системи.
