## 1. Executive Verdict

**GO - bounded Phase 5 may proceed.**

Phase 5 for this repository is **not** guarded authority. Phase 5 is the first bounded step from shadow-only verdict production to real downstream verdict consumption while preserving existing runtime ownership. The runtime target is `hybrid_advisory`, and the only permitted downstream effect is a **decision_making-owned, monitoring-only consultation event** derived from a matched ENTRY `JudgeVerdict`.

The frozen Phase 5 decision is:

1. Admit `hybrid_advisory` at runtime alongside `off` and `shadow`.
2. Consume ENTRY `JudgeVerdict` only.
3. Keep `guarded_entry_authority` and `guarded_lifecycle_authority` rejected at config load.
4. Keep `applied=False` mandatory for `hybrid_advisory`.
5. Implement consultation in `decision_making` via a bounded bridge that correlates verdicts and strategy signals by exact same-cycle identity.
6. Emit one new monitoring event, `EVT:JUDGE_ADVISORY_CONSULTED_V1`, when an eligible advisory verdict is matched.
7. Do **not** mutate `EVT:STRATEGY_SIGNAL_PRODUCED`, `StrategyGateway`, `IntentBuilder`, `TRADE_INTENT_PROPOSED`, `execution_position`, or exchange-facing behavior.

This blueprint does **not** reopen any Phase 1-4 contract, placement, or ownership decision.

## 2. Authority Model

### 2.1 Concept Authority

The governing concept defines the semantic ceiling of the mode vocabulary:

- `off`: no judge runtime.
- `shadow`: judge runs, emits, and logs, but is not consumed.
- `hybrid_advisory`: verdicts may be consulted by `decision_making`, but `decision_making` is not bound.
- `guarded_entry_authority`: future entry authority.
- `guarded_lifecycle_authority`: future lifecycle authority.

The concept laws remain in force:

- Judge is advisory/policy only, never execution truth owner.
- No direct LLM-to-exchange path exists.
- Replayability and auditability remain mandatory.

### 2.2 Repo Truth from Phases 1-4

Repo-resident truth is stricter than the long-range concept sequence:

- Phase 1 froze contracts, schemas, vocabulary, and placement.
- Phase 2 admitted only `off` and `shadow` and revived the legacy experts.
- Phase 3 added chamber aggregation and admissibility while keeping shadow posture.
- Phase 4 added evidence envelopes and deterministic verdict synthesis, still shadow-only.

The shipped repository therefore ends Phase 4 with full verdict production and zero semantic consumption.

### 2.3 Phase 5 Reconciliation Rule

The concept's long-range naming places guarded entry authority after hybrid advisory. The current repository directive for Phase 5 is narrower: **the first bounded step toward verdict consumption while preserving ownership safety**. Therefore, for this repository line:

- `hybrid_advisory` is the Phase 5 runtime deliverable.
- `guarded_entry_authority` is deferred to Phase 6 or later.
- `guarded_lifecycle_authority` remains deferred.

This is a deliberate scope freeze, not an unresolved ambiguity.

### 2.4 Ownership Rule

Ownership in Phase 5 is fixed as follows:

- `alpha_search` owns verdict production.
- `decision_making` owns verdict consultation.
- `execution_position` remains judge-blind.
- No judge payload may cross the execution boundary.

## 11. Advisory Consumption Design

### 11.1 Consumed Artifact

The only consumed artifact in Phase 5 is:

- `JudgeVerdict` from `EVT:JUDGE_ENTRY_VERDICT_V1`

Phase 5 does **not** consume:

- `ExpertOutput`
- `ChamberAggregate`
- `JudgeEvidenceEnvelope`
- `EVT:JUDGE_LIFECYCLE_VERDICT_V1`

### 11.2 Consumer Owner and Dependency Boundary

The consumer is a new DM-local module:

- `apps/reference/domains/decision_making/judge_advisory_bridge.py`

This module may import the shared contract model `JudgeVerdict` from the judge contract surface. It may **not** import alpha-search runtime internals such as:

- `backtest_plugin.py`
- chamber internals
- expert internals
- envelope assembler internals

### 11.3 Correlation Key

Exact same-cycle correlation is mandatory and frozen to:

`(strategy_id, symbol, tf_sec, bar_close_ts)`

Field derivation is frozen as follows:

- from strategy signal: `strategy_id`, `symbol`, `tf_sec`, `bar_close_ts`
- from judge verdict: `strategy_id`, `symbol`, `tf_sec`, `ts_ms`

For the verdict side, `ts_ms` is treated as cycle `bar_close_ts`. This relies on the already-delivered Phase 4 timestamp alignment fix.

Signal `ts_ms` or wall-clock timestamps must **not** be used for matching.

### 11.4 Order-Agnostic Bridge State

The bridge must work when the verdict arrives before the signal and when the signal arrives before the verdict.

Minimum required state:

| State | Key | Contents | Eviction Rule |
|-------|-----|----------|---------------|
| `pending_signals` | `(strategy_id, symbol, tf_sec, bar_close_ts)` | minimal signal snapshot | evict on match or when a newer `bar_close_ts` is seen for the same `(strategy_id, symbol, tf_sec)` |
| `pending_verdicts` | same key | validated ENTRY `JudgeVerdict` snapshot | evict on match or when a newer `bar_close_ts` is seen for the same `(strategy_id, symbol, tf_sec)` |
| `emitted_consultations` | `consultation_id` | dedupe tombstone | prevent duplicate emission for the same cycle |

No scheduler, timer wheel, or shared config is required. Phase 5 is explicitly same-cycle-only.

### 11.5 Consultation Emit Semantics

The bridge behavior is frozen:

1. On `EVT:JUDGE_ENTRY_VERDICT_V1` ingress:
   - validate payload as `JudgeVerdict`;
   - reject anything whose `authority_mode` is not `hybrid_advisory`;
   - reject anything whose `applied` is not `False`;
   - store verdict by exact key;
   - if a pending signal with the same key exists, emit consultation and clear the pair.

2. On `EVT:STRATEGY_SIGNAL_PRODUCED` handling inside `DecisionMaking`:
   - extract minimal same-cycle signal identity;
   - store signal by exact key;
   - if a pending eligible verdict with the same key exists, emit consultation and clear the pair.

3. On observing a newer `bar_close_ts` for the same `(strategy_id, symbol, tf_sec)`:
   - evict any unmatched older signal/verdict state;
   - emit nothing;
   - change no decision behavior.

### 11.6 New Event Contract

Phase 5 adds exactly one new event:

- `EVT:JUDGE_ADVISORY_CONSULTED_V1`

Ownership and routing:

- owner: `decision_making`
- target domains: `monitoring`
- status: `experimental`

Required payload fields:

| Field | Meaning |
|-------|---------|
| `consultation_id` | deterministic cycle id, one per matched consultation |
| `strategy_id` | copied from both matched artifacts |
| `symbol` | copied from both matched artifacts |
| `tf_sec` | copied from both matched artifacts |
| `bar_close_ts` | same-cycle correlation timestamp |
| `signal_side` | side from the matched strategy signal |
| `verdict_id` | matched judge verdict id |
| `envelope_id` | matched verdict envelope id |
| `chamber_id` | matched chamber id |
| `entry_verdict` | matched ENTRY verdict |
| `confidence` | verdict confidence |
| `dissent_noted` | verdict dissent flag |
| `reasoning` | verdict reasoning list |
| `authority_mode` | must be `hybrid_advisory` |
| `applied` | must be `false` |
| `schema_version` | fixed `"1"` |

This event is the **only** Phase 5 downstream consultation artifact.

### 11.7 Fail-Closed Rules

Fail-closed behavior is frozen exactly as follows:

| Condition | Phase 5 Behavior |
|-----------|-------------------|
| No verdict for the same key yet | keep pending signal state only |
| No signal for the same key yet | keep pending verdict state only |
| Newer cycle arrives before match | evict unmatched older state silently |
| Verdict `authority_mode != hybrid_advisory` | ignore verdict |
| Verdict `applied != False` | ignore verdict and log warning |
| Verdict scope is lifecycle | ignore verdict |
| Matched verdict is `OPEN_LONG` or `OPEN_SHORT` | emit consultation event |
| Matched verdict is `NO_ENTRY` or `UNKNOWN` | still emit consultation event; no decision mutation |

Fail-closed here means one thing only: **no match or invalid match must never change decision or execution behavior**.

## 13. Phase 5 Runtime / Event Flow

Frozen Phase 5 runtime flow:

1. `CMD:PROCESS_STRATEGY` enters the existing runtime.
2. `alpha_search` runs providers; judge experts remain active whenever judge mode is not `off`.
3. If judge mode is `shadow` or `hybrid_advisory`, chamber aggregation runs for enabled verdict scopes.
4. Evidence envelope assembly runs exactly as in Phase 4.
5. Verdict synthesis runs exactly as in Phase 4 except `authority_mode` now reflects the live judge mode.
6. `EVT:JUDGE_ENTRY_VERDICT_V1` is emitted from `alpha_search`.
7. `decision_making` advisory bridge receives the verdict event and either stores it or matches it to a pending signal.
8. Independently, the existing strategy path emits `EVT:STRATEGY_SIGNAL_PRODUCED`.
9. `DecisionMaking._on_strategy_signal_gateway()` first hands the signal to the advisory bridge and then forwards the signal to `StrategyGateway` unchanged.
10. If an exact eligible verdict-signal pair exists, the bridge emits `EVT:JUDGE_ADVISORY_CONSULTED_V1`.
11. `StrategyGateway`, `IntentBuilder`, and `execution_position` continue unchanged.
12. When a newer bar arrives for the same strategy/symbol/timeframe tuple, any older unmatched advisory state is evicted.

Order-independence is mandatory:

- verdict first, then signal -> emit on signal side;
- signal first, then verdict -> emit on verdict side.

In both cases, the consultation event is monitoring-only and has no effect on trade intent creation.

## 2. Why the Current Draft Was Rejected

### Defect 1: Confusing operational modes with rollout phases

**Evidence:** The governing concept (Section 12) defines rollout phases independently from operational modes. The mode table (Section 4) maps `hybrid_advisory` to "Phase 4+" meaning it becomes *eligible* starting from Phase 4 onward. The rollout table (Section 12) defines what each phase *actually implements*:

- Phase 5 = "Guarded entry authority. StrategyGateway gate insertion."

The current Phase 4 implementation deferred advisory to "Phase 4b or Phase 5" (Phase 4 Blueprint, Inference I1). The prior Phase 5 draft treated this deferral as proof that Phase 5 *must* implement advisory consumption. This is a non-sequitur: the deferral means advisory was not ready in Phase 4, not that Phase 5 is the correct place to implement it without validation.

**Why it matters:** Jumping from shadow-only to advisory consumption without an intermediate validation step violates Concept Law 5 (shadow-first) in spirit. The shadow pipeline produces artifacts, but nobody has verified whether those artifacts contain economically meaningful signal. Promoting unvalidated verdicts to advisory status -- even "non-binding" advisory -- is premature.

This is consistent with Concept Law 5 (shadow-first validation) and the user operational intent ("advisory behavior must be explicit, bounded, auditable").

**Why it matters:** Granting advisory visibility or authority to unvalidated verdicts wastes operator trust. If verdicts are economically wrong, advisory exposure teaches operators to ignore them. The simulator produces calibration evidence BEFORE any promotion.

**Evidence:** The prior draft introduced runtime admission widening (`hybrid_advisory`), decision_making consultation, signal annotation, and advisory telemetry. All of these are promotion-track artifacts that presume verdict quality has been validated.

## 12. Shadow Economic Simulator Design

### 12.1 Purpose

The Shadow Economic Simulator is an **offline replay engine** that reads judge shadow artifacts (JSONL logs), correlates them with realized price paths, applies fee/slippage models, and produces calibration datasets and disagreement diagnostics.

It answers the question: **If we had followed judge verdicts, what would the economic outcomes have been?**

### 12.2 Consumed Artifacts

| Artifact | Source | Used For |
|----------|--------|----------|
| `JudgeVerdict` JSONL | `logs/judge_shadow/verdict_{symbol}_{date}.jsonl` | Primary input: verdict direction, confidence, dissent |
| `JudgeEvidenceEnvelope` JSONL | `logs/judge_shadow/envelope_{symbol}_{date}.jsonl` | Regime enrichment, features_ref for context |
| `ChamberAggregate` JSONL | `logs/judge_shadow/chamber_{symbol}_{date}.jsonl` | Per-expert accuracy breakdown, consensus quality |
| `ExpertOutput` JSONL | `logs/judge_shadow/{expert_id}_{symbol}_{date}.jsonl` | Individual expert accuracy, weight calibration |
| Price data (bars/candles) | Feature cache JSONL or candle data source | Forward-return computation |
| Virtual trader closed positions | `backtest_plugin.closed_positions` (runtime) or JSONL if persisted | Hold/no-hold comparison baseline |

**Justification for consuming all 4 judge artifact types:**
- `JudgeVerdict` alone is insufficient: the simulator needs expert-level accuracy to calibrate confidence weighting.
- `ChamberAggregate` provides consensus metrics needed for disagreement diagnostics.
- `JudgeEvidenceEnvelope` provides regime context needed to stratify outcomes by market condition.
- `ExpertOutput` enables per-expert accuracy breakdown for future expert weight tuning.

### 12.3 Simulator Inputs

For each verdict record, the simulator needs:

```
verdict_record:
    symbol: str
    ts_ms: int               # verdict timestamp (= bar close timestamp)
    entry_verdict: str        # OPEN_LONG | OPEN_SHORT | NO_ENTRY | UNKNOWN
    confidence: float
    dissent_noted: bool
    chamber_admissibility: str  # from envelope -> chamber_aggregate
    consensus_direction: str
    expert_outputs: list      # from chamber_aggregate

price_path:
    prices_at_horizons:       # close prices at ts_ms + each horizon
        5m: float
        15m: float
        30m: float
        60m: float            # optional extended horizon

fee_model:
    taker_fee_bps: float      # basis points per side (e.g., 4.0 = 0.04%)
    slippage_bps: float       # basis points of adverse slippage (e.g., 2.0)
```

### 12.4 What Is Simulated

#### 12.4.1 Verdict-vs-Outcome Cohort Classification

Each verdict is classified into an outcome cohort based on realized forward returns:

| Verdict | Forward Return Direction | Cohort | Meaning |
|---------|------------------------|--------|---------|
| OPEN_LONG | positive | CORRECT_ENTRY | Verdict was directionally correct |
| OPEN_LONG | negative | INCORRECT_ENTRY | Verdict was directionally wrong |
| OPEN_SHORT | negative (price down) | CORRECT_ENTRY | Verdict was directionally correct |
| OPEN_SHORT | positive (price up) | INCORRECT_ENTRY | Verdict was directionally wrong |
| NO_ENTRY | any | CORRECT_ABSTAIN or MISSED_OPPORTUNITY | Judged by whether magnitude exceeds threshold |
| UNKNOWN | any | INCONCLUSIVE | Verdict was unavailable; cannot evaluate |

#### 12.4.2 Fee/Slippage-Adjusted Economic Outcome

For each OPEN_LONG or OPEN_SHORT verdict:

```
raw_return = (exit_price - entry_price) / entry_price * direction_sign
round_trip_cost = 2 * (taker_fee_bps + slippage_bps) / 10000
net_return = raw_return - round_trip_cost
```

`entry_price` = close price at verdict `ts_ms`.
`exit_price` = close price at `ts_ms + horizon`.
`direction_sign` = +1 for LONG, -1 for SHORT.

#### 12.4.3 Hold/No-Hold Comparison

For each verdict cycle where the virtual trader also had an active position:

| Scenario | Description |
|----------|------------|
| Verdict agrees with VT position | Both LONG or both SHORT: measure alignment rate |
| Verdict disagrees with VT position | Verdict says opposite: measure disagreement cost |
| Verdict says NO_ENTRY, VT has position | Measure whether abstaining would have been better |
| Verdict says OPEN_X, VT has no position | Measure whether entering would have been profitable |

This produces a 2x2 confusion matrix of judge-vs-virtual-trader decisions.

#### 12.4.4 Disagreement Diagnostics

For each verdict where the optimal action (with hindsight) differs from the verdict:

```
disagreement_record:
    verdict_id: str
    symbol: str
    ts_ms: int
    verdict_action: str       # what the judge said
    optimal_action: str       # what hindsight says
    cost_of_disagreement: float  # net return difference (fee-adjusted)
    regime: Optional[str]     # from envelope
    confidence: float
    dissent_noted: bool
    expert_breakdown: list    # which experts were correct/incorrect
```

Disagreement records are the highest-value output of the simulator: they identify WHERE and WHY the judge is wrong, stratified by regime, confidence level, and expert composition.

#### 12.4.5 Per-Expert Accuracy Breakdown

For each expert in each verdict's `ChamberAggregate.expert_outputs`:

```
expert_accuracy_record:
    expert_id: str
    symbol: str
    ts_ms: int
    expert_entry_verdict: str
    realized_direction: str    # UP | DOWN | FLAT
    correct: bool
    confidence: float
```

Aggregated across all records: per-expert accuracy rate, per-expert accuracy-by-regime, per-expert accuracy-by-confidence-bucket.

#### 12.4.6 Calibration Dataset

The simulator produces a structured calibration dataset:

```
calibration_entry:
    symbol: str
    ts_ms: int
    verdict: str
    confidence: float
    dissent_noted: bool
    regime: Optional[str]
    admissibility: str
    horizon_5m_net_return: float
    horizon_15m_net_return: float
    horizon_30m_net_return: float
    cohort: str                # CORRECT_ENTRY | INCORRECT_ENTRY | CORRECT_ABSTAIN | MISSED_OPPORTUNITY | INCONCLUSIVE
    expert_accuracy: dict      # {expert_id: correct (bool)}
```

This dataset is the primary input for a future Promotion Review (Phase 6+). It enables:
- Confidence threshold calibration: "at what confidence level does following the verdict become profitable?"
- Expert weight tuning: "which experts are most accurate by regime?"
- Disagreement cost budgeting: "what is the maximum disagreement cost we accept before promotion?"

### 12.5 Replayability and Forensic Outputs

All simulator outputs are:
1. Written to JSONL in a dedicated directory (`logs/judge_simulator/`)
2. Timestamped and linkable to source verdict_id
3. Deterministic given the same JSONL input + price data + fee config
4. Replayable: re-running the simulator on the same inputs produces identical outputs

```python
class SimulatorConfig(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    enabled: bool = False
    shadow_log_dir: str = "logs/judge_shadow"
    output_dir: str = "logs/judge_simulator"

```

Fields:

- `shadow_log_dir`: Where to read verdict/envelope/chamber/expert JSONL. Default matches shadow log default.

- `horizons_sec`: Forward-return measurement horizons in seconds. Default [300, 900, 1800] = 5m, 15m, 30m.
- `missed_opportunity_threshold_bps`: Minimum forward return magnitude (bps) for NO_ENTRY to count as MISSED_OPPORTUNITY vs CORRECT_ABSTAIN. Default 10.0.
- `min_confidence_for_entry`: Minimum verdict confidence to count as an "actionable" entry verdict. Default 0.0 (all entries counted).

## 18. Risks

### R1: Price Data Availability for Forward Returns

- **Cause:** Simulator needs prices at `ts_ms + horizon` but bar data may not be available at exact horizon timestamps.
- **Mechanism:** If price data is sparse or unavailable, forward returns cannot be computed.
- **Effect:** Simulator produces incomplete calibration datasets.
- **Severity:** MEDIUM
- **Mitigation:** Use nearest-bar interpolation. PriceSource abstraction allows multiple backends. If no price data, mark record as INCONCLUSIVE and skip.

### R2: JSONL Log Volume and Parse Performance

- **Cause:** Large shadow runs produce large JSONL files. Parsing all at once may be slow.
- **Mechanism:** O(N) file reads for each symbol/date combination.
- **Effect:** Simulator run time may be slow for large datasets.
- **Severity:** LOW (offline operation; no runtime impact)
- **Mitigation:** Stream parsing (line-by-line). Optional date filtering to limit scope.

### R3: Hindsight Bias in Outcome Classification

- **Cause:** Forward returns are computed with perfect hindsight. Real execution would face uncertainty.
- **Mechanism:** Calibration datasets may overstate predictive accuracy.
- **Effect:** Overconfident promotion decisions.
- **Severity:** MEDIUM
- **Mitigation:** Fee/slippage model adds friction. Multi-horizon analysis reduces single-point bias. Document limitation in calibration output.

### R4: Virtual Trader Position Correlation

- **Cause:** Virtual trader positions and verdict timestamps may not align perfectly.
- **Mechanism:** Hold/no-hold comparison may misattribute outcomes.
- **Effect:** Incorrect hold/no-hold confusion matrix.
- **Severity:** LOW (both share bar_close_ts from same cycle)
- **Mitigation:** Correlation by (symbol, ts_ms) key. Tolerance window for near-matches.

### R5: Simulator Config Omitted by Operator

- **Cause:** Operator runs shadow mode but does not add `simulator:` config section.
- **Mechanism:** Simulator never runs. No calibration evidence produced.
- **Effect:** Promotion review has no data.
- **Severity:** LOW (simulator is optional; absence is safe)
- **Mitigation:** Document recommended workflow. Simulator can be run retroactively on historical JSONL.
