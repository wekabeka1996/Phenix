# Реалізовані функції домену Account Balance

## Огляд

Домен `account_balance` реалізує клас `AccountConnector` з набором методів для моніторингу стану рахунку Binance Futures. Всі методи використовують асинхронне програмування та обробку помилок для забезпечення надійності.

## Основний клас: AccountConnector

### Конструктор та ініціалізація

#### `__init__(fsm: FSMCore, config: Dict[str, Any]) -> None`
**Опис:** Ініціалізує з'єднання з Binance API через BinanceAdapter.

**Параметри:**
- `fsm`: Екземпляр FSM core для емісії подій
- `config`: Конфігураційний словник з API credentials та налаштуваннями

**Логіка ініціалізації:**
1. Збереження посилань на FSM та конфігурацію
2. Отримання інтервалу опитування з `account_observer.poll_interval`
3. Вибір API конфігурації залежно від `trading_mode`:
   - `live`: Використання бойових API ключів
   - `testnet`/`hybrid`: Використання тестових API ключів
4. Валідація наявності всіх необхідних API параметрів
5. Створення екземпляра `BinanceAdapter`

**Викидає:** `ValueError` при неповній API конфігурації

### Управління життєвим циклом

#### `start() -> None`
**Опис:** Запускає моніторинг рахунку у фоновому потоці.

**Логіка:**
1. Перевірка, чи вже запущено
2. Встановлення прапора `running = True`
3. Створення daemon потоку з методом `_monitor_loop`
4. Запуск потоку
5. Логування успішного запуску

#### `stop() -> None`
**Опис:** Зупиняє моніторинг та закриває з'єднання.

**Логіка:**
1. Встановлення `running = False`
2. Очікування завершення потоку (thread.join())
3. Закриття HTTP сесії адаптера
4. Логування зупинки

### Основний цикл моніторингу

#### `_monitor_loop() -> None`
**Опис:** Головний цикл моніторингу, що працює у фоновому потоці.

**Логіка:**
1. Створення нового event loop для асинхронних операцій
2. Цикл поки `running == True`:
   - Виклик `_fetch_and_emit_account_data()`
   - Очікування `update_interval` секунд
3. Закриття event loop при завершенні

**Обробка помилок:** Логування завершення циклу

### Отримання та обробка даних

#### `_fetch_and_emit_account_data() -> None`
**Опис:** Асинхронно отримує дані з Binance API та емітує FSM події.

**Логіка для балансу:**
1. Виклик `adapter.get_account_balance()`
2. Валідація типу відповіді (має бути list)
3. Збереження даних у `_latest_balance_data`
4. Детальне логування USDT балансу
5. Виклик `_emit_balance_update()`

**Логіка для позицій:**
1. Виклик `adapter.get_open_positions()`
2. Валідація типу відповіді (має бути list)
3. Виклик `_emit_positions_update()`

**Обробка помилок:** Окрема обробка для балансу та позицій з детальним логуванням

### Емісія FSM подій

#### `_emit_balance_update(balance_data: List[Dict[str, Any]]) -> None`
**Опис:** Емітує подію `EVT:BALANCE_UPDATE_RECEIVED` з даними балансу.

**Трансформація даних:**
1. Фільтрація активів з `balance > 0`
2. Конвертація числових значень у `Decimal` для точності
3. Створення списку assets з полями:
   - `asset`: назва активу
   - `balance`: загальний баланс
   - `crossUnPnl`: нереалізований P&L
   - `crossWalletBalance`: баланс cross margin
   - `updateTime`: час оновлення

**Payload структури:**
```python
{
    'assets': [...],  # список активів
    'updateTime': int  # максимальний updateTime з активів
}
```

**Емісія події:**
- Event name: `"EVT:BALANCE_UPDATE_RECEIVED"`
- Why: `"Balance data updated from Binance API."`
- Логування кількості активів з балансом > 0

#### `_emit_positions_update(positions_data: List[Dict[str, Any]]) -> None`
**Опис:** Емітує подію `EVT:ACCOUNT_UPDATE_RECEIVED` з даними позицій та загального стану.

**Трансформація позицій:**
1. Фільтрація позицій з `positionAmt != 0`
2. Конвертація у Decimal для точності
3. Створення списку відкритих позицій з полями:
   - `symbol`: торгова пара
   - `positionAmt`: розмір позиції
   - `entryPrice`: ціна входу
   - `unRealizedProfit`: нереалізований прибуток
   - `leverage`: плече
   - `marginType`: тип маржі
   - `markPrice`: позначена ціна
   - `liquidationPrice`: ціна ліквідації

**Розрахунок загального стану:**
1. Використання `_latest_balance_data` для USDT активу
2. Отримання `totalWalletBalance` з поля `balance`
3. Отримання `totalUnrealizedProfit` з поля `crossUnPnl`
4. Отримання `totalCrossWalletBalance` з відповідного поля

**Payload структури:**
```python
{
    'totalWalletBalance': str,
    'totalUnrealizedProfit': str,
    'totalCrossWalletBalance': str,
    'positions': [...],  # список відкритих позицій
    'updateTime': int    # поточний timestamp в ms
}
```

**Емісія події:**
- Event name: `"EVT:ACCOUNT_UPDATE_RECEIVED"`
- Why: `"Open positions data updated from Binance API."`
- Логування кількості відкритих позицій та wallet balance

## Внутрішні атрибути класу

### Конфігураційні атрибути
- `fsm`: Посилання на FSM core
- `config`: Конфігураційний словник
- `update_interval`: Інтервал опитування в секундах (за замовчуванням 30)

### Стан виконання
- `thread`: Фоновий потік виконання
- `running`: Прапор активності моніторингу
- `adapter`: Екземпляр BinanceAdapter

### Кешовані дані
- `_latest_balance_data`: Останні дані балансу з API `/fapi/v2/balance`

## Використовувані зовнішні залежності

### vfoundation.adapters.binance_adapter.BinanceAdapter
**Методи:**
- `get_account_balance()`: Отримання балансу активів
- `get_open_positions()`: Отримання відкритих позицій
- `close_session()`: Закриття HTTP сесії

### vfoundation.core.FSMCore
**Методи:**
- `emit(event_name, payload, why)`: Емісія FSM події

## Обробка помилок

### Стратегії
1. **API помилки:** Логування з `exc_info=True` для детального traceback
2. **Невалідні дані:** Перевірка типів та пропуск некоректних записів
3. **Мережеві проблеми:** Graceful degradation з останніми відомими даними

### Логування
- **INFO:** Успішні операції, кількість даних
- **WARNING:** Відсутність USDT, проблеми з даними
- **ERROR:** Критичні помилки з повним traceback

## Продуктивність

### Оптимізації
- **Фільтрація:** Тільки активи з балансом > 0 та позиції з amount != 0
- **Кешування:** Збереження балансу для використання в позиціях
- **Асинхронність:** Неблокуючі API виклики
- **Background execution:** Окремий потік не блокує основний процес

### Метрики використання
- **CPU:** Мінімальне навантаження (тільки періодичні API виклики)
- **Memory:** Фіксований розмір для кешування останніх даних
- **Network:** 2 API виклики кожні 30 секунд
- **Storage:** Не використовує постійне сховище

## Тестування

### Модульні тести
- **Ініціалізація:** Валідація конфігурації та створення адаптера
- **API моки:** Симуляція відповідей Binance API
- **Трансформація:** Перевірка конвертації даних у події
- **Емісія:** Валідація структури payload подій

### Інтеграційні тести
- **FSM інтеграція:** Перевірка емісії та споживання подій
- **API інтеграція:** Тестування з реальними credentials (testnet)
- **Error handling:** Симуляція мережевих помилок та API failures

## Безпека

### Захист облікових даних
- API ключі передаються тільки через конструктор
- Не логуються у звичайному режимі
- Використання HTTPS через BinanceAdapter

### Аудит
- Всі API виклики логуються без sensitive data
- Детальне логування фінансових операцій
- Timestamp всіх операцій для аудиту
