# План Інтеграції LLA та vFoundation

**Версія:** 1.0
**Дата:** 2025-10-26
**Автор:** Gemini AI Agent

## 1. Мета проєкту

Головна мета — інтегрувати самонавчальний оркестратор LLA (Living Latent Agent) з існуючою доменною архітектурою vFoundation. Це перетворить систему зі статичної, керованої правилами федерації FSM, на динамічну, адаптивну систему, яка самостійно оптимізує послідовність взаємодії між своїми компонентами. Кінцевою ціллю є автоматична максимізація прибутковості (`+PnL`) при дотриманні заданих обмежень ризику (`-CVaR`), стабільності та продуктивності.

## 2. Вимоги до функціоналу

### Функціональні вимоги:
-   **Збір даних:** LLA має отримувати події (`events`) та метрики (`metrics`) з усіх ключових доменів vFoundation (execution, risk, data_provider) через стандартизовані "мости" (Bridges).
-   **Оркестрація:** LLA (в ролі Meta-FSM/CA-FSM) має керувати потоком виконання, динамічно вирішуючи, який домен і коли активувати.
-   **Навчання та Адаптація:** Система повинна аналізувати результати своїх дій через "Осьовий Градієнт" (Axial Gradient) і поступово змінювати параметри своєї логіки (ваги, пороги), щоб покращити показник AG.
-   **Безпека Адаптацій:** `Proof Kernel` повинен валідувати кожну запропоновану адаптацію на відповідність фундаментальним інваріантам безпеки (LTL Invariants). Жодна зміна, що порушує безпеку, не повинна бути застосована.
-   **Управління:** LLA має надсилати команди (наприклад, зміна параметрів ризику, ініціація дій) назад у домени vFoundation через `CommandBridge`.
-   **"Тіньовий" режим (Shadow Mode):** Система повинна підтримувати режим, у якому LLA навчається на реальних даних, але його команди лише логуються, а не виконуються.

### Нефункціональні вимоги:
-   **Надійність:** Система повинна бути відмовостійкою. Збій одного з компонентів не повинен призводити до каскадного збою. Механізми відновлення стану (DR/Hydration) мають бути збережені та розширені для LLA.
-   **Продуктивність:** Критичний "гарячий шлях" (hot path) всередині доменів vFoundation має відповідати існуючим SLO (p95 ≤ 50ms). Цикл адаптації LLA є "холодним шляхом" (cold path) і може виконуватися з меншою частотою (наприклад, раз на кілька секунд/хвилин).
-   **Прозорість (Observability):** Кожне рішення LLA та кожна адаптація повинні мати чіткий "причинний слід" (`causal_trace`) та записуватися в лог для подальшого аналізу.
-   **Підтримуваність:** Інтерфейси між LLA та vFoundation (мости) мають бути чітко визначені, слабко зв'язані та задокументовані, щоб спростити подальшу розробку.

## 3. Технологічний стек

-   **Мова програмування:** Python 3.11
-   **Основний фреймворк:** vFoundation (існуюча кодова база)
-   **Оркестратор:** LLA (на основі кодової бази з `LLA-r2-ci-harden-cvar-dod`)
-   **Контракти даних:** YAML (словники) та JSON Schema 2020-12
-   **Валідація даних (Runtime):** Pydantic
-   **Тестування:** Pytest, `unittest.mock`
-   **Інфраструктура:** Локальна файлова система для логів, WAL, станів. Архітектура має бути готова до майбутньої інтеграції з хмарними сховищами (напр., S3).

## 4. Етапи розробки (з термінами)

План базується на інкрементальному підході, описаному в `vFoundation_LLA.md`.

-   **Sprint 0: Підготовка та закриття боргів (3-4 дні)**
    -   **Завдання:** Написати відсутні юніт- та інтеграційні тести для існуючої бази vFoundation, виявлені під час аудиту (ідемпотентність, гідратація, portfolio risk, E2E).
    -   **DoD:** Покриття тестами критичних компонентів > 95%. Всі тести "зелені".

-   **Sprint A: Інфраструктура та Мости (Bridges) (2-3 дні)**
    -   **Завдання:** Створити структуру директорій (`foundation/adapters/`, `foundation/meta_fsm/`). Реалізувати базові `EventBridge`, `MetricBridge`, `CommandBridge`, які поки що лише логують дані у файли. Інтегрувати виклики `EventBridge` у ключові точки доменів vFoundation.
    -   **DoD:** Файл `logs/causal_events.jsonl` наповнюється подіями з доменів під час тестового прогону.

-   **Sprint B: Каркас CA-FSM (3-4 дні)**
    -   **Завдання:** Інтегрувати базову логіку `CAFSM` з `run_r0.py`. Налаштувати головний цикл, який реагує на події з мостів і приймає рішення на основі *статичної* (поки що) конфігурації переходів з `ca_fsm.yaml`.
    -   **DoD:** Система здатна провести один повний "епізод" (від сигналу до умовного закриття позиції) під керуванням CA-FSM.

-   **Sprint C: Осьовий Градієнт (AG) та Оцінювач (3-4 дні)**
    -   **Завдання:** Реалізувати `axial_gradient.py` та `evaluator.py`. Підключити їх до `CAFSM` для розрахунку та логування значення AG для кожного епізоду. **Тюнер адаптацій вимкнено (log-only)**.
    -   **DoD:** Файл `logs/ag_eval.jsonl` наповнюється реалістичними значеннями AG.

-   **Sprint D: Proof Kernel (4-6 днів)**
    -   **Завдання:** Реалізувати мінімальний `Proof Kernel` з базовими LTL-інваріантами (напр., "не відкривати дублюючі позиції"). Інтегрувати його як "запобіжник", який перевіряє команди від LLA.
    -   **DoD:** Спроба LLA згенерувати небезпечну команду (в тесті) блокується, і цей факт логується в `logs/proof_record.jsonl`.

-   **Sprint E-G: Інтеграція, CI та 72-годинний "тіньовий" прогін (5-7 днів)**
    -   **Завдання:** Повністю інтегрувати всі компоненти. Налаштувати CI для запуску всіх тестів. Запустити систему в режимі "Shadow Mode" на 72 години. Активувати базовий тюнер адаптацій.
    -   **DoD:** Система стабільно працює 72 години без критичних помилок. AG демонструє позитивну динаміку. `R2_72H_READY=YES`.

**Орієнтовний загальний час:** 4-6 тижнів.

## 5. Критерії успіху (KPI)

-   **Технічні KPI:**
    -   Успішне завершення 72-годинного "тіньового" прогону без критичних помилок.
    -   Покриття тестами нового коду (мости, LLA-адаптери) > 95%.
    -   Кількість спрацювань `Proof Kernel` (блокувань небезпечних дій) дорівнює 0 у стабільному режимі.
-   **Бізнес-KPI (в режимі симуляції):**
    -   Позитивна динаміка середнього значення Осьового Градієнта (`AG`) протягом "тіньового" прогону.
    -   Перевершення показників (Sharpe, Profit Factor) статичної версії архітектури на тих самих історичних даних.

## 6. Ризики та їх мінімізація

-   **Ризик 1: Технічний борг у тестах.**
    -   *Опис:* Початок інтеграції LLA на недостатньо протестованій базі vFoundation може призвести до важкодіагностованих помилок.
    -   *Мінімізація:* **Виконати Sprint 0 (закриття боргів по тестах) перед початком активної інтеграції LLA.**
-   **Ризик 2: Складність інтеграції.**
    -   *Опис:* Неправильне проєктування "мостів" може призвести до сильної зв'язаності (tight coupling) між LLA та vFoundation.
    -   *Мінімізація:* Суворо дотримуватися "contract-first" підходу для мостів. Інтерфейси мають бути мінімалістичними та асинхронними.
-   **Ризик 3: Нестабільне навчання LLA.**
    -   *Опис:* На початкових етапах LLA може генерувати хаотичні або неоптимальні послідовності команд, що призведе до "тремтіння" системи.
    -   *Мінімізація:* Запускати LLA з вимкненим тюнером (log-only) на перших етапах. Використовувати `Proof Kernel` як жорсткий запобіжник. Проводити тривалі прогони в "shadow mode".

## 7. План тестування

1.  **Юніт-тести:** Кожен новий модуль (`EventBridge`, `AxialGradient`, `ProofKernel` і т.д.) буде покрито власним набором юніт-тестів.
2.  **Інтеграційні тести:**
    -   Тестування кожного "моста" окремо (напр., чи правильно `MetricBridge` агрегує дані з `PositionTracking`).
    -   Тестування повного циклу LLA з імітованими (mocked) доменами vFoundation.
3.  **E2E (End-to-End) Тестування:**
    -   Головним E2E тестом є **72-годинний "тіньовий" прогін**, який валідує поведінку всієї системи на реальних даних.
4.  **Регресійне тестування:** Повний набір тестів (`pytest`) буде запускатися в CI після кожної значної зміни.

## 8. План розгортання

Розгортання буде відбуватися поетапно, з поступовим підвищенням рівня ризику.

1.  **Етап 1: Shadow Mode (Тіньовий режим).** LLA працює з реальними ринковими даними, приймає рішення, але його команди лише логуються. Система не виконує реальних угод.
2.  **Етап 2: Paper Trading (Паперова торгівля).** `CommandBridge` налаштовується на відправку ордерів на тестовий (паперовий) акаунт біржі.
3.  **Етап 3: Live Limited (Обмежений реальний режим).** Система запускається на реальному акаунті з мінімальним капіталом та для одного, найбільш стабільного інструменту.
4.  **Етап 4: Live Full (Повний реальний режим).** Поступове збільшення капіталу та кількості торгових інструментів під постійним моніторингом KPI.

## 9. План підтримки

-   **Моніторинг:** Налаштування дашбордів для відстеження ключових KPI (середній AG, PnL, drawdown, кількість LTL-порушень, стан "мостів"). Налаштування автоматичних сповіщень (alerts) на критичні помилки та порушення інваріантів.
-   **Логування:** Усі артефакти LLA (`causal_events.jsonl`, `ag_eval.jsonl`, `proof_record.jsonl`) мають централізовано збиратися, архівуватися та бути доступними для аналізу.
-   **План відкату (Rollback Plan):** Має існувати чітка процедура для негайного відключення адаптивного механізму LLA. Це можна реалізувати через "feature flag", який перемикає систему назад до статичної логіки оркестрації, минаючи `CAFSM`.
