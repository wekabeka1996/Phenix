

# ЕТАП 7 — RUST ЯК ФОРМАЛІЗАЦІЯ БЕЗПЕЧНИХ СИСТЕМ

*(ownership, borrowing, lifetimes, unsafe)*

## Ціль етапу 7

Перетворити неформальні інтуїції з Етапів 4–6 у **формальні гарантії**:

* закріпити **lifetime як first-class концепт**
* зрозуміти **ownership як інваріант**

* чітко відрізняти **safe** від **unsafe** і знати, навіщо існує друге

Після цього етапу ти **бачиш небезпеку в дизайні ще до коду**.

## УРОК 7.0 — Навіщо взагалі Rust

**Теза:** Rust існує, щоб **забороняти неправильні стани на етапі компіляції**.

**Терміни:** memory safety, data race freedom, compile-time guarantees.

**Практика:**

* Пояснити, які баги з Етапів 4–6 Rust забороняє принципово
* Пояснити, які **не** забороняє

**Міні-тест:**

* “Чому Rust не замінює інженерне мислення?”

---

## УРОК 7.1 — Ownership як інваріант

**Теза:** ownership — це **право відповідальності за ресурс**.

**Терміни:** ownership, move, drop, scope.

**Практика:**

* Намалювати lifetime ресурсу від створення до drop
* Пояснити, чому copy ≠ move

**Міні-тест:**

* “Що станеться, якщо власників буде два?”

---

## УРОК 7.2 — Borrowing: тимчасовий доступ

**Теза:** borrowing — це **контрольований доступ без передачі власності**.

**Терміни:** borrow, immutable borrow, mutable borrow.

**Практика:**

* Пояснити правило: “один mutable або багато immutable”
* Навести приклад, де правило рятує від гонки

**Міні-тест:**

* “Чому mutable borrow ексклюзивний?”

---

## УРОК 7.3 — Lifetimes як час існування

**Теза:** lifetime — це **часова межа валідності посилання**.

**Терміни:** lifetime, scope, annotation.

**Практика:**

* Пояснити, чому посилання не може жити довше за власника
* Намалювати два перекривні lifetimeʼи

**Міні-тест:**

* “Чому lifetime — не тип?”

---

## УРОК 7.4 — Borrow Checker як формальний доказ

**Теза:** borrow checker — це **машина доведення інваріантів**.

**Терміни:** borrow checker, constraint, inference.

**Практика:**

* Розібрати типову помилку компілятора построково
* Пояснити, який інваріант порушено

**Міні-тест:**

* “Чому компілятор ‘занадто суворий’, але правий?”

---

## УРОК 7.5 — Struct, ownership і дизайн

**Теза:** дизайн структур = дизайн володіння.

**Терміни:** struct, field ownership, composition.

**Практика:**

* Проєктування struct з явним ownership
* Пояснити, які поля володіють, а які позичають

**Міні-тест:**

* “Чому поганий дизайн структури ускладнює borrowing?”

---

## УРОК 7.6 — Enums і контроль станів

**Теза:** enum — це **обмеження можливих станів**.

**Терміни:** enum, variant, exhaustive match.

**Практика:**

* Побудувати enum для станів системи
* Пояснити, як match змушує обробити всі варіанти

**Міні-тест:**

* “Чому enum зменшує кількість багів?”

---

## УРОК 7.7 — Error handling як дизайн

**Теза:** помилки — це **частина контракту**, не виняток.

**Терміни:** Result, Option, error propagation.

**Практика:**

* Спроєктувати API з Result
* Пояснити, чому panic — не стратегія

**Міні-тест:**

* “Чому явні помилки краще за приховані?”

---

## УРОК 7.8 — Concurrency у Rust (на високому рівні)

**Теза:** Rust переносить інваріанти concurrency в типову систему.

**Терміни:** Send, Sync, thread safety.

**Практика:**

* Пояснити, чому деякі типи не `Send`
* Звʼязати це з гонками з Етапу 6

**Міні-тест:**

* “Чому не кожен тип можна передати між потоками?”

---

## УРОК 7.9 — Unsafe: контрольований вихід

**Теза:** unsafe — це **місце, де інженер бере відповідальність**.

**Терміни:** unsafe block, safety invariant.

**Практика:**

* Виписати інваріанти, які має гарантувати unsafe-код
* Пояснити, чому unsafe обмежений блоками

**Міні-тест:**

* “Чому unsafe не робить код ‘поганим’?”

---

## УРОК 7.10 — Rust як інженерний фільтр

**Теза:** Rust не прискорює мислення — він **карає за неінженерне мислення**.

**Терміни:** design pressure, correctness by construction.

**Практика:**

* Порівняти один і той самий дизайн у C і Rust
* Пояснити, де Rust змусив переосмислити архітектуру

**Міні-тест:**

* “Що Rust змінює в твоєму підході до дизайну?”

## СР-7B — “Unsafe-контракт”

Описати:

* для чого потрібен unsafe
* які інваріанти він має гарантувати
* що буде, якщо їх порушити

# Контрольна робота №7

**Частина 1 — Аналіз**

* знайти порушення ownership
* пояснити borrow-помилку
* виписати інваріанти unsafe-коду

**Частина 2 — Причини**

1. Чому ownership — інваріант, а не зручність?
2. Чому borrow checker — доказ, а не обмеження?
3. Чому lifetimes — про час, а не синтаксис?
4. Чому unsafe — необхідне зло?

**Критерій зарахування:**

* чіткі інваріанти
* відсутність “магії”
* причинно-наслідкове мислення

## Appendix E7 — Rust: ownership, borrowing, lifetimes, unsafe (Етап 7)

**Мільстоун:** *“Safe core + unsafe boundary contract”*

* Реалізувати маленький компонент:

	* safe API назовні
	* якщо є unsafe — то тільки як тонкий шар із **явно прописаними safety invariants**
* Зібрати 10 borrow-ошибок і для кожної пояснити: який інваріант порушено.

**Інструменти:**

* `cargo test`, `clippy`, базовий `rustfmt`
* читання compile errors як “доказів”.

**Історична причина:**

* Rust — відповідь на десятиліття катастроф із пам’яттю та гонками: ідея “заборонити неправильні стани” на етапі компіляції.

**Зарахування:**

* Ти **не воюєш** з borrow checker — ти вмієш через нього **перепроєктувати дизайн**.
