

# ЕТАП 5 — ОПЕРАЦІЙНІ СИСТЕМИ

*(процеси, віртуальна памʼять, syscall, scheduler)*

## Ціль етапу 5

Сформувати **інженерну модель ОС як менеджера ресурсів і причинності**:

* що таке **процес** і чому це не “програма”
* де проходить **межа user / kernel**
* як **віртуальна памʼять** створює ілюзії
* що реально відбувається при **syscall**
* як **scheduler** керує часом CPU

Після цього етапу:

* зникає “магія ОС”
* ти бачиш, **де виникає latency**
* інтуїтивно розумієш, **що безпечно, а що небезпечно робити в user-space**

## УРОК 5.0 — Навіщо взагалі потрібна ОС

**Теза:** ОС — це **арбітр ресурсів**, а не “сервіс для програм”.

**Терміни:** operating system, resource management, abstraction, isolation.

**Практика:**

* Пояснити: що буде, якщо програми напряму керують CPU і памʼяттю
* Скласти список ресурсів, які контролює ОС

**Міні-тест:**

* “Чому без ОС система стає небезпечною?”

---

## УРОК 5.1 — Процес як одиниця виконання

**Теза:** процес — це **контейнер стану**, а не код.

**Терміни:** process, PID, address space, context.

**Практика:**

* Намалювати процес: код + памʼять + регістри
* Пояснити різницю між програмою і процесом

**Міні-тест:**

* “Чи може одна програма мати кілька процесів?”

---

## УРОК 5.2 — Створення процесу: fork / exec

**Теза:** `fork` копіює **стан**, `exec` змінює **вміст**.

**Терміни:** fork, exec, parent, child.

**Практика:**

* Покроково описати: fork → два процеси
* Пояснити, чому fork без exec — рідко корисний

**Міні-тест:**

* “Чому fork не копіює всю памʼять фізично?”

---

## УРОК 5.3 — Межа user / kernel

**Теза:** kernel — це **привілейований світ**, user — обмежений.

**Терміни:** user space, kernel space, privilege, protection.

**Практика:**

* Намалювати межу user/kernel
* Пояснити, що user-код **не може** робити напряму

**Міні-тест:**

* “Чому не можна виконати syscall без переходу в kernel?”

---

## УРОК 5.4 — System Call як контрольований вхід

**Теза:** syscall — це **офіційний тунель** у kernel.

**Терміни:** system call, trap, context switch.

**Практика:**

* Покроково описати `read()`:
  user → trap → kernel → I/O → повернення
* Пояснити, де виникає overhead

**Міні-тест:**

* “Чому syscall повільніший за звичайну функцію?”

---

## УРОК 5.5 — Контекстне перемикання

**Теза:** context switch — це **зміна активного стану CPU**.

**Терміни:** context switch, registers, scheduler.

**Практика:**

* Перелічити, що зберігається при context switch
* Пояснити, чому це коштовно

**Міні-тест:**

* “Чому багато процесів = latency?”

---

## УРОК 5.6 — Віртуальна памʼять: ілюзія адрес

**Теза:** віртуальна памʼять — це **фейкова карта реальності**.

**Терміни:** virtual memory, physical memory, address translation.

**Практика:**

* Намалювати: virtual → physical
* Пояснити, чому кожен процес “бачить” однакові адреси

**Міні-тест:**

* “Чому без VM немає ізоляції?”

---

## УРОК 5.7 — Page Tables і MMU (концептуально)

**Теза:** MMU — апаратний перекладач адрес.

**Терміни:** MMU, page table, page, mapping.

**Практика:**

* Пояснити, що робить MMU на кожному доступі до памʼяті
* Намалювати спрощену page table

**Міні-тест:**

* “Чому VM потребує hardware підтримки?”

---

## УРОК 5.8 — Page Fault

**Теза:** page fault — це **нормальний механізм**, не помилка.

**Терміни:** page fault, demand paging, swap.

**Практика:**

* Описати сценарій page fault
* Пояснити, чому він повільний

**Міні-тест:**

---

## УРОК 5.9 — Scheduler і час CPU

**Теза:** scheduler вирішує, **хто отримує час**.

**Терміни:** scheduler, time slice, fairness, priority.

**Практика:**

* Пояснити, чому “швидкий код” може чекати
* Намалювати таймлайн 3 процесів

**Міні-тест:**

* “Чому latency ≠ throughput?”

## УРОК 5.10 — Інженерний погляд на ОС

**Теза:** ОС — це **джерело як стабільності, так і складності**.

**Терміни:** overhead, isolation, scalability.

**Практика:**

* Сформулювати 5 інженерних правил взаємодії з ОС

## Appendix E5 — ОС: процеси, VM, syscall, scheduler (Етап 5)

**Мільстоун:** *“Process lifecycle simulation + syscall budget”*

* Взяти сценарій: процес запускається, читає файл/мережу, створює дочірній процес, завершується.
* Описати: де trap/syscall, де context switch, де page fault можливий, де overhead.

**Інструменти:**

* `strace` (бачити syscalls як “скелет поведінки”),
* `top/htop`, базовий аналіз процесів.

**Історична причина:**

* ОС еволюціонували, щоб забезпечити **ізоляцію** і **спільне використання ресурсів** (мультипрограмність), а VM стала фундаментом безпеки/стабільності.

**Зарахування:**

* Ти не плутаєш: segfault vs page fault, процес vs програма, syscall vs function call.

> **Важливо:** тут же тримаємо “Network-minimum” як частину етапу, а не окремий етап.
