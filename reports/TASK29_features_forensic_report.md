## 🧩 Detailed Forensic Evidence

### 1) Macro Sync / Correlation (Epps Effect)
The current implementation computes returns between consecutive ticks of the trading symbol and correlates them with returns of anchors (BTC/ETH).
*   **Evidence:** `calculation_engine.py:427-431` iterates through price deques to calculate returns.
*   **The Bug:** Returns are not synchronized to a common time grid (resampling). A "window" of 60 returns for DOGE might cover 2 seconds, while 60 returns for BTC covers 200ms. Correlating these without resampling to e.g. 1-second bins results in a massive **Epps Effect**, biasing correlation towards 0 and rendering the "Macro Sync" signal meaningless for high-frequency regime detection.

### 2) Large Trade / Imbalance (Lost Information)
The aggregator intended to detect institutional flow is functionally broken.
*   **Evidence:** In `websocket_aggregator.py:152`, the trade `quantity` (pld `q`) is received but **not stored** in the `trades_window`.
*   **The Bug:** 
    1.  `sell_trades` and `buy_trades` are simple counters (+1 per trade).
    2.  `calculation_engine.py:330` attempts to divide `buy_volume` (which is actually `buy_count`) by a missing field `buy_count`, resulting in a default to `neutral_value`.
    *   **Result:** Institutional "block trades" are indistinguishable from "retail dust" in the current features.

### 3) Volume Spike dt Normalization
The claim that volume spikes are "WS artifacts" is refuted in the current version.
*   **Evidence:** `MarketDataWorker` maps Binance `E` (Event Time) to the `ts` field.
*   **Logic:** `FeatureEngineering` calculates `time_diff = current_tick["ts"] - last_tick["ts"]`. Since `ts` is exchange-derived, the `rate = volume / dt` calculation is stable across network jitters.

### 4) Volatility / Welford Stability
The risk of sliding window divergence (negative M2) is mitigated.
*   **Evidence:** `FeatureUtils.welford_remove` (lines 232-234) contains:
    ```python
    if m2_new < eps or n_new < 1:
        m2_new = 0.0
    ```
*   **Note:** While stable, a "hard reset" every 10k ticks is still recommended for production as per best practices.
