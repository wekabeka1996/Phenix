# Фаза 3: Аналіз Розподілу Ознак (Feature Distribution Analysis)

## Мета
Використовуючи зібрані у Фазі 2 проблемні таймстемпи, проаналізувати значення розрахованих ознак (features), щоб знайти оптимальну математичну межу між "справжнім трендом" та "тимчасовою корекцією".

## Джерела даних
*   `logs/features/*.log` (зокрема файли для проблемних символів, наприклад `SOLUSDT.log` або `ETHUSDT.log`).
*   Список "Canary Таймстемпів" з Фази 2.

## Кроки виконання

1.  **Видобуток ознак (Feature Extraction):**
    *   Написати парсер для `logs/features/*.log`, який ефективно читатиме ці великі файли.
    *   Витягти значення ключових індикаторів для моментів блокування (NRR-027). Основні кандидати для перевірки:
        *   `trend_strength` / `trend_confidence`
        *   `regime_score`
        *   `ema_distance` або `z_score` (якщо використовуються для напрямку)
        *   `order_book_imbalance`
2.  **Візуалізація та Статистичний Аналіз (EDA):**
    *   Побудувати гістограми розподілу значень трендового індикатора для двох класів подій:
        *   **Клас А (Справжні блокування):** Ціна продовжила падіння (для LONG). NRR-027 відпрацював правильно.
        *   **Клас Б (Помилкові блокування - FP):** Ціна розвернулася вгору (для LONG). NRR-027 спрацював помилково на дні корекції.
3.  **Пошук Оптимального Порогу (Threshold Tuning):**
    *   Визначити нові значення порогів (наприклад, змінити вимогу до `min_trend_confidence` з 0.6 на 0.75, або додати умову врахування RSI/Imbalance).
    *   Знайти таку комбінацію умов, яка максимізує пропуск подій "Клас Б" (дозволяє торгувати), при цьому залишаючи заблокованими щонайменше 80% подій "Клас А" (захист від тренду залишається).

## Очікуваний результат
Чітко визначені нові параметри для `DirectionalSanityGate` (наприклад, нові пороги у YAML конфігах). Відповідно, підготовка патчу для `config/aurora/...`
