# Глибокий аналіз архітектури Alpha Search та аудит коду

**Дата:** 01.02.2026
**Статус:** Phase 1-4 Complete (Prototype)

Цей документ містить детальний розбір роботи системи Alpha Search після воскресіння, а також чесний аудит виявленого "технічного боргу" (хардкоду).

---

## І. Як це працює тепер (Архітектура Alpha Search Resurrection)

Ми створили "Тіньовий Мозок" (Shadow Brain), який живе всередині бектестера, але ізольований від основної торгової логіки.

### 1. Етап Фундаменту: Векторизоване збагачення (`feature_augmenter.py`)
Замість того, щоб рахувати індикатори "на льоту" для кожної свічки (що повільно), ми робимо це **векторизовано** одразу після завантаження даних `load_data()`.
*   **Polars/NumPy:** Ми беремо весь масив цін за рік і одним махом рахуємо MACD, RSI, Stochastic та Momentum.
*   **Результат:** Ваші дані для бектесту (`self.feed`) тепер містять не тільки OHLCV, а й готові сигнали технічного аналізу.

### 2. Етап Спостереження: Плагін (`backtest_plugin.py`)
Ми впровадили "шпигуна" — `AlphaSearchBacktestPlugin`.
*   Він слухає подію `EVT:FEATURES_CALCULATED` (або мусить слухати `EVT:MARKET_TICK` з розширеними даними).
*   Коли надходить нова свічка, плагін непомітно передає її в **Ансамбль**.
*   **Shadow Mode:** Плагін генерує сигнали, записує їх у лог, але **не відправляє** ордери на біржу.

### 3. Етап Вирішення: Ансамбль та Голосування (`ensemble.py`)
Це серце системи. Три моделі голосують:
1.  **Momentum:** "Тренд — твій друг" (використовує RSI + Momentum).
2.  **Mean Reversion:** "Ціна повернеться до середнього" (BBands + Stoch).
3.  **Volatility:** "Ринок надто спокійний/активний".

Ансамбль зважує їхні голоси. Якщо Momentum каже "Купуй" (впевненість 0.8), а інші мовчать, Ансамбль формує загальний `AlphaScore`.

### 4. Етап Навчання: Feedback Loop (`on_trade_result`)
Це головна інновація.
*   Коли бектестер закриває віртуальну угоду (`EVT:TRADE_EXECUTED`), плагін викликає `ensemble.on_trade_result()`.
*   Він каже Ансамблю: *"Твій сигнал ID #123 п'ять хвилин тому приніс би +$50 прибутку"*.
*   Ансамбль оновлює ваги: успішні моделі отримують більше впливу на наступний голос.

## ІІ. Аудит коду: "Магічні числа" та Хардкод

Я провів ревізію коду. Висновок: **система перенасичена хардкодом**. Це допустимо для Research-прототипу, але потребує виправлення перед Scale-up.

### 1. Backtest Engine (`feature_augmenter.py`) — "Жорсткі стандарти"
*   **MACD (12, 26, 9):** Ці параметри "зашиті" як дефолтні аргументи функцій. Щоб змінити їх, треба правити код виклику в `engine.py`.
*   **Momentum Windows [5, 60, 1440]:** Це числа `5 хвилин`, `1 година`, `1 день`. Вони прив'язані до 1-хвилинних барів. Якщо запустити бектест на 4-годинних свічках, логіка "денного" моментуму (1440 барів) дасть збій (рахуватиме 1440 * 4 години).

### 2. Моделі (`momentum.py` і т.д.) — "Магічні числа"
Логіка містить емпіричні константи (Magic Numbers):
*   `short_weight = 0.3`, `medium_weight = 0.4` — Гіпотетичний розподіл ваг без можливості конфігурації.
*   `multiplier = 1.2` — Коефіцієнт підсилення об'ємом. Емпіричне число.
*   `RSI Thresholds (70/30)` — Класичні пороги, жорстко прописані в коді.
*   `Confidence 0.8` — Захардкоджена базова впевненість.

### 3. Плагін та Ансамбль — "Бракує гнучкості"
*   **Threshold 0.1:** Сигнал вважається `LONG`, якщо score > 0.1. Чому не 0.05?
*   **Normalization 100.0:** У функції `on_trade_result` PnL ділиться на 100.0. Це "магічне число" для нормалізації. Якщо капітал зросте, це число перестане працювати коректно.

## ІІІ. Критична знахідка (Wiring Gap)

Під час аудиту `engine.py` (рядки 408-430) я виявив, що формування події `EVT:MARKET_TICK` відбувається вручну:

```python
payload = {
    "ts": ts_ms,
    "symbol": row["symbol"],
    "price": close_px,
    ...
}
```

**Проблема:** `BacktestEngine` **ігнорує** нові колонки (MACD, RSI), які ми додали на етапі Augmentation. Вони залишаються в DataFrame, але не потрапляють у подію.
**Наслідок:** `FeatureEngineering` (і як наслідок Alpha Plugin) може отримувати неповні дані.
